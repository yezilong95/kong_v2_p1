# 无障碍自愈 · 落地方案（B 包自行恢复）

> 目标：B 包（`com.android1IN42343.client`）的无障碍被系统或厂商清掉之后，**不再依赖安装器 A 包、也不再依赖服务端 adb**，由 App 自己恢复。
> 口径：**只写策略、机制与验收标准，不含代码**。分层与验收格式沿用 `详情页超时-落地方案.md`。
> 前置分析：`docs/1688无障碍自愈机制-分析.md`（竞品机制还原 + CPH2783 真机实测结论）。本文的判定顺序与修法选择**直接采用该文档 §7.5 / §7.6 的实测结论**。

---

## 零、为什么必须是「配对时授权 → App 自己修」

一个很容易被提出的方案是：无障碍掉了，就用服务端 adb 把它打开。**这条路由不通，而且原因是循环依赖**：

1. 服务端要连上手机，必须 `adb pair`。
2. 配对要 SPAKE2 握手，配对码和连接端口只能从手机屏幕上的「无线调试」页读出来。
3. 读那页的唯一手段是**无障碍**（`AdbWirelessAutomator.collectVisibleTexts` → `AccessibilityControlBridge.dumpUiTree`）。
4. 无障碍已经死了 → 读不到配对码 → 配不上 → 拿不到 adb → 开不了无障碍。

**所以「用 adb 修无障碍」在无障碍已死的前提下永远不可达。** 唯一能打破循环的时机是**无障碍还活着的时候**——也就是第一次配对成功的那个瞬间。

于是方案定形为：

| 时机 | 动作 |
|---|---|
| **第一次（人工）** | 人打开「无线调试」页 → 服务端配对成功 → **顺手 `pm grant` 一个能力权限** |
| **之后（全自动）** | App 靠这个权限自己改写系统设置，把无障碍写回来 |

> 用户已确认：**第一次能手工进无线调试页就行**，之后由 App 自己修复。

## 一、关键事实（决定方案形态的四条）

以下是真机（Infinix X6838 / Android 14，`121624048Y103638`）实测结论，不是推断：

1. **`WRITE_SECURE_SETTINGS` 可以授给普通应用。**
   该权限 `prot = signature | privileged | development | installer`，带 `development` 标志，因此 `adb shell pm grant` 合法。`pm grant` 返回 `rc=0`，`dumpsys package` 显示 `granted=true`。
2. **必须先声明，才能授予。**
   清单里没写该权限时，`pm grant` 抛 `SecurityException: ... has not requested permission`。**旧版本包拿不到**，只有声明后的版本才行。
3. **覆盖安装保留授权，换包名从零开始。**
   同 `applicationId` 覆盖安装 `granted` 保持 `true`；改包名（换马甲）则必须重新走一次配对授权。这是马甲体系下必须知道的成本。
4. **`am force-stop` 会清空无障碍设置项。**
   测试与救急时注意：这个动作本身就会把 `enabled_accessibility_services` 变成 `null`。

> 另一条与判定直接相关（分析文档 §7.5 / §7.6）：**只有 component 列表起作用**。单独把 `accessibility_enabled` 写成 1 而列表为空，`Bound services` 仍是空集；反过来，列表里有我们时把开关改成 0，服务**照样保持绑定**。所以开关值不能当首要判据。

## 二、四态模型

判定只依赖两个事实：**列表里有没有我们**、**服务实例在不在**。开关值只用于「列表里没有」时的日志区分。

| 状态 | 列表含本组件 | 服务已绑定 | 含义 | 修法 |
|---|---|---|---|---|
| `NORMAL` | ✓ | ✓ | 健康 | 不动 |
| `ORPHANED` | ✓ | ✗ | 配置在、系统没绑 | **toggle 重绑**（摘掉再写回） |
| `NOT_BOUND` | ✗ | ✗ | 开关开着但没配我们 | `restore`（写入新值即生效） |
| `DISABLED` | ✗ | ✗ | 开关也关着 | `restore`（写入列表 + 补开关） |

**判定顺序必须是「先看列表，再看开关」**。现有 `AccessibilityHelper.getServiceStatus()` 把 `!isAccessibilityManagerEnabled()` 放在最高优先级，会在「开关 0 但服务照样绑着」时误报 `disabled`——这正是分析文档 §7.6 记录的反直觉现象。自愈路径不走那个函数。

**`ORPHANED` 只能 toggle 修复，不能重写同值。** 同值 `putString` 不产生 SettingsProvider 的变更通知，`AccessibilityManagerService` 收不到，也就不会重新 bind。真机对照实验：

| 手段 | 结果 |
|---|---|
| `settings put secure enabled_accessibility_services <同值>` | 不触发重绑 |
| 切 `accessibility_enabled` 0 → 1 | 不触发重绑 |
| **摘掉组件 → 写回组件** | **恢复绑定** |

## 三、分层落地

### L1 · 能力层（服务端：配对时顺手授权）

**范围**：`Manage/api/src/services/adb/adb-grant-permissions.ts`（新增）、`Manage/api/src/services/adb-relay.service.ts`。

**策略**
- 配对成功后、`adbSessionRegistry.register()` 之后，执行一次能力授权：
  - `android.permission.WRITE_SECURE_SETTINGS`（自愈必需）
  - `android.permission.PACKAGE_USAGE_STATS`（顺带，无副作用）
- **包名解析优先用设备上的事实**：先从 `dumpsys accessibility` 反查已注册的 `RemoteAccessibilityService` 组件并截出包名；查不到才退回仓库配置。马甲号每期换名，只读配置会授错包。
- **以 `dumpsys package` 为准，不看 `pm grant` 的退出码**。旧包没声明该权限时会抛 `SecurityException`，退出码和真实结果不对应。
- **授权失败绝不影响配对结论**。这一步是 best-effort：配对已经成功，把它判成失败会让前端以为没连上，反而拆掉刚建好的会话。
- 结果透传给前端，让人能看见「授成功了没有」，而不是黑盒。

**验收**

| 项 | 标准 |
|---|---|
| 新包装机配对后 | 设备端 `dumpsys package <pkg>` 显示 `WRITE_SECURE_SETTINGS: granted=true` |
| 旧包（未声明该权限）配对 | 配对仍 `ok=true`，grant 结果里该权限 `granted=false` 且 detail 说明原因 |
| 前端配对结果 | 明确显示「已授予 WRITE_SECURE_SETTINGS，客户端可自愈无障碍」或失败明细 |
| 幂等 | 重复配对不重复报错，已授予的权限标 `already_granted` |

---

### L2 · 执行层（客户端：判定 + 写回）

**范围**：`AccessibilityHealth.kt`（判定真源 + 唯一写入口）、`AccessibilitySelfHeal.kt`（执行器）。

**策略**

1. **唯一写入口**。所有系统设置写入集中在一处，落点固定为
   `enabled_accessibility_services` + 必要的 `accessibility_enabled`，**顺序必须先写列表、后写开关**（反过来会被系统按旧开关状态判一次，出现短暂解绑）。

2. **无权限时整条路径 no-op**。没有 `WRITE_SECURE_SETTINGS` 就完全不碰系统设置，只记一行 `reason=no_wrss`。这让默认开启对存量装机**零副作用**。

3. **`ORPHANED` 先等再 toggle**。进程刚起 / 刚被 FCM 拽起来时，`onServiceConnected` 往往还没回调，`isConnected` 是 false 而列表和开关都正常。这是「伪 ORPHANED」，开机一次必中一次。所以：
   - 先给一段 bind 观察窗口（5 × 300ms）；
   - 绑上了 → `action=bind_delayed`，不做任何写入；
   - 仍没绑 → `action=rebound`，走 toggle。

4. **写成功后要等，不要瞬间判定**。settings 写完到 `onServiceConnected` 之间是异步的（实测 60–800ms）。瞬间复查会稳定误报「写了但没救回来」，把连续失败计数一路顶到退避阈值，之后**正常的**巡检反而被限流。所以写成功后给 5 × 300ms 的观察窗口。

5. **限频与退避**。两次尝试最小间隔 60s；连续失败 3 次后拉长到 10 分钟。避免 toggle 风暴把系统 bind 队列打满。

6. **构建开关** `A11Y_SELF_HEAL`，默认 `true`（有权限才动作，所以默认开是安全的）；`-PA11Y_SELF_HEAL=0` 可整体关闭。

**触发点**（多入口冗余，任一命中即可）

| 入口 | 场景 |
|---|---|
| 巡检协程 | 每 30s 一次，冷启动宽限 10s（`ConnectionService`） |
| FCM 唤醒 | 进程被冻结时唯一被放行的入口，正是最需要自愈的时刻 |
| 开机 / 覆盖安装 | `BOOT_COMPLETED`、`MY_PACKAGE_REPLACED` |
| Watchdog 闹钟 | 5 分钟一跳，最稳的兜底 |
| 服务端命令 | `heal_accessibility`，强制、忽略限频，供人肉排查 |

**验收**

| 项 | 标准 |
|---|---|
| 抹掉列表与开关 | ≤ 2 个巡检周期（约 60s）内恢复，日志 `action=restored healed=true` |
| `ORPHANED` 真修复 | 摘写后 `Bound services` 重新出现，`action=rebound` |
| 伪 ORPHANED | 覆盖安装/冷启动后 `action=bind_delayed`，**不产生摘写** |
| 无权限 | 日志 `reason=no_wrss`，系统设置完全不变 |
| 限频 | 刚成功过之后 60s 内不再重复写 |
| 三种状态互不干扰 | 单次故障只增一次 `consecutiveFailures`，不误入退避 |

### L3 · 让位层（不能把运维的主动操作顶回去）

**范围**：`CommandExecutor.executeUninstall()`、`RemoteAccessibilityService.onServiceConnected()`、`SetupPrefs`。

**问题**：`uninstall` / `disable_accessibility` 命令的语义就是「故意关掉无障碍，准备卸载」。巡检若不加区分地自愈，会把它 30 秒内写回来——运维看到的现象是**关不掉**，卸载流程永远走不完。

**策略**
- 主动关闭时先写抑制时间戳（`a11y_self_heal_suppressed_until`），**有界 30 分钟**。
  - 为什么有界：卸载中途被取消时还能自己恢复，不留永久哑火。
  - 落 Device-Protected：抑制期间进程多半正在被杀。
- 抑制**连 `force` 也不越过**。主动关闭是有意为之，任何入口都不该翻回来。
- `onServiceConnected` 时解除抑制。用户/运维重新打开无障碍这一刻，抑制自动失效，不需要额外接口。
- 抑制状态在日志里可见（`skip ... reason=suppressed`），便于排查「为什么不自愈」。

**验收**

| 项 | 标准 |
|---|---|
| 下发 `uninstall` 后 | 至少 2 个巡检周期内无障碍保持关闭，日志 `reason=suppressed` |
| 抑制到期 / 手动清除 | 重启进程后下一轮巡检立即恢复，`healed=true` |
| 用户手动重开无障碍 | `onServiceConnected` 清抑制，之后巡检恢复正常工作 |

## 四、整体验收矩阵

| 场景 | 预期 | 已验证 |
|---|---|---|
| 新装 + 配对 | `WRITE_SECURE_SETTINGS granted=true` | ✓ 真机 |
| 旧包配对（未声明） | 配对成功，grant 失败但不影响结论 | ✓ 真机 |
| 覆盖安装 | 授权保留、无障碍可用 | ✓ 真机 |
| 列表被清空 | ≤ 60s 自愈，`action=restored` | ✓ 真机 |
| 开关改 0 但服务绑着 | **不误判**，不产生写入 | ✓ 真机 |
| `ORPHANED` | toggle 有效；同值重写/切开关无效 | ✓ 真机（shell 复现写入序列） |
| 无 `WRITE_SECURE_SETTINGS` | 完全 no-op | ✓ 真机 |
| 主动关闭后 | 抑制生效，不自愈 | ✓ 真机 |
| 抑制解除 | 下一轮立即恢复 | ✓ 真机 |

## 五、已知边界与不做的事

1. **不做「服务端 adb 开无障碍」**。原因见 §零，是循环依赖，不是实现难度问题。
2. **不做「重启 App 恢复」**。实测拉进程不能让服务重新绑定；只有 toggle 可以（分析文档 §7.5 实验 C 对照）。
3. **不依赖 `cmd accessibility enable`**。该机型 `cmd accessibility` 只有 `help` / `set-bind-instant` / `call-system-action` / `trace`，没有 `enable`。服务端里那行 `.catch(() => undefined)` 是死代码。
4. **Marshall 级别不可达的场景仍然要靠人**：用户主动在系统设置里关掉无障碍、换包名重装（授权清零）、厂商硬性禁止。这三种由向导页引导，不自愈。
5. **`am force-stop` 会清空无障碍**。这是测试/救急动作的副作用，不是自愈的缺陷。
6. **`WRITE_SECURE_SETTINGS` 依赖清单声明**。因此存量老包升级到该版本后，**需要再配对一次**才能拿到授权；未配对前自愈静默不动作。

## 六、上线顺序

1. **App 发版**：清单加 `WRITE_SECURE_SETTINGS` + 自愈逻辑。此版本对未授权设备完全 no-op，可安全先发。
2. **服务端发版**：配对成功后自动 grant，前端展示结果。
3. **存量设备**：跑一次配对（人工停到无线调试页），之后即进入自愈覆盖。
4. **观察口径**：按 `A11ySelfHeal` 标签统计 `action` 分布——`bind_delayed` 多说明判定偏保守（正常），`rebound` 多说明系统确实在掉绑（需要查厂商），`no_wrss` 多说明授权没铺开。
