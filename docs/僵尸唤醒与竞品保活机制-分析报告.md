# 僵尸唤醒失效 · 与竞品保活机制对照分析报告

> 现象：后台点击「唤醒僵尸」→ 服务端返回 `needWake:true`，但设备不亮屏、不执行。
> 口径：**只写结论、机制与验收标准，不含代码**。所有结论均标注证据来源；未经实机验证的推断单独标记 `[待验证]`。
> 测试机：Infinix X6838（Transsion/MTK），`com.android1IN42343.client`。uid 会随重装漂移（本轮见过 `10308` / `10310`），文中出现的 uid/pid 只对当时那次安装有效，见 §7.7。

## 零、结论摘要

本机厂商的 **Hiber 冻结**（`TranHiberManager`）按 **uid 整体**把进程组塞进 `5:freezer:/frozen`，冻结期间进程**一行代码都跑不了**。因此闹钟、WS 心跳、HTTP 轮询、JobScheduler，**任何"唤醒来执行代码"的手段都无效**——不是没被叫醒，而是被叫醒了也无法运行。

唯一的例外是 Hiber 广播白名单里的 `com.google.android.c2dm.intent.RECEIVE`：它会在投递**之前**把 uid 解冻，给进程一个约 5 秒的执行窗口（§4.7）。这是本机唯一获准穿透冻结的普通 app 通道，也是整个方案的支点。

原本的计划是「加一把常驻 `PARTIAL_WAKE_LOCK` 阻止进入冻结」（抄竞品 `p2.java:4497`）。**本次实机 A/B 已证伪这条路径**：

| 组 | 配置 | 灭屏后结果 |
|---|---|---|
| A | `KEEPALIVE_WAKE_LOCK=off` | `22:15:09` 进入 `/frozen`，此后 polls 恒为 1 |
| B1 | `partial`（tag `RemoteControl:KeepAlive`） | 灭屏瞬间 `Force remove wakelock`，`22:31:57` frozen |
| B2 | `partial-job`（tag `*job*RemoteControl:KeepAlive`） | 同样 `Force remove`，`22:35:28` frozen |
| B3 | `partial-audio`（tag `AudioMix:...`，系统**放行**） | `isMatchFilterCondition is audio` 放行，但 `22:41:31` 仍被 Hiber 冻结 |

三条硬结论：

1. **`PowerManagerService` 会定期清锁**：灭屏后 10s，凡 tag 不含 `Audio`/`FmService`/`BtOppObexServer` 的 PARTIAL 锁一律 `Force remove`。
2. **即使 tag 命中放行名单，`Hiber` 照样冻结**。两套机制独立，绕过前者不等于绕过后者。
3. **竞品的 `icp:SocketCPU` 在本机也活不过 10 秒**——它在本机能"陆续上线"，靠的不是这把锁。

于是必须重新回答：**竞品到底靠什么在本机活下来？** 见 §四.6（`SilentMusicService` + FCM `wake_all`）。

**FCM 通道已实机验证通过**（§4.7）：

| 结论 | 证据 |
|---|---|
| `c2dm.intent.RECEIVE` 能解冻进程 | `Hiber: unfreeze uid 10308 reason:broadcast cpninfo:com.google.android.c2dm.intent.RECEIVE` |
| 解冻窗口仅 ~5.1 秒 | `22:54:12.866 /` → `22:54:17.916 /frozen`，与 `frozenDelay=5000` 吻合 |
| **亮屏期间不会重新冻结** | `23:10:43` 仍为 `/`，亮屏已 2 分 17 秒；灭屏 20s 后重进 `/frozen` |
| 端到端可亮屏常亮 | `wake done overlayOk=true keepActive=true`，持续 5 分钟直到 `keepAwakeMs` 到期 |

保活模型因此确定为：**一个 5 秒的广播窗口，换一次 5 分钟亮屏；亮屏期间进程免冻结**。消息必须自带 `wakeUntil`，不能回 HTTP 取参数——窗口太窄。

**Firebase 工程接入已完成**（§4.8），并解决了两个会让发版中断的问题：

| 问题 | 解法 |
|---|---|
| google-services 插件用 `package_name` 比对 `applicationId`，马甲换包名即构建失败 | 构建期先解析 json，**匹配才 apply 插件**；不匹配自动降级，`FCM_ENABLED=false` |
| 声明生产权限后 adb 再也发不出这条广播，后续无法验证 | `fcmReceiverPermission` 占位符，默认 `c2dm.permission.SEND`，验证时 `-PFCM_RECEIVER_PERMISSION=android.permission.DUMP` |

服务端走 topic `wake_all` 群发，未配置 Service Account 时静默降级（不抛错）。真实凭证已就位，并在生产机端到端跑通：设备 `frozen` + 灭屏 → 服务端 `nudgedFcm:true` → `c2dm` 到达 → 解冻 → 亮屏，全程 **1.04 秒**（§八）。

**服务端这条链在测试机上曾被误判为代码问题，实际是出口墙**：`8.155.130.49` 到 Google 的 443 全不通（`http=000`，IP 层封锁），`send()` 必然超时。同一份代码同一份凭据换到 `47.84.116.171` 就通了。排障口诀：**先 `curl` 测出口，再翻代码**（§7.8.1）。

**最后一道拦路虎是自家黑洞 VPN**（§4.9）。它把 `com.google.android.gms` 加进白名单后，GMS 的 FCM 注册流量进了"只读不写"的 TUN，表现为 `SERVICE_NOT_AVAILABLE`、订阅 Task 永不回调。竞品 `PpVpn` 同样把 GMS 加进白名单却没事，因为它**只在安装器 A 前台并装完 B 之后才停**，且真正常驻的 B 包里根本没有 `VpnService`；A 再次启动会直接跳去 B，永远不再建 VPN（§4.9.3）。我方虽然同样是 A/B 双包，但 **B 自己也带一个 `BlackholeVpnService`**，而 B 是常驻进程、永远不会"退到后台"，于是 VPN 从安装完成一直挂到进程死亡，GMS 全程被黑洞。

修复方向是恢复竞品的生命周期语义（`STOP_VPN_AFTER_SETUP=1`，setup 完成后真正停掉），已在实机跑通完整链路：冻结 → FCM 到达 → 解冻（`reason:wakelock`）→ 亮屏。

**但 `STOP_VPN_AFTER_SETUP` 这条路最终被证伪，改为直接把 B 包的 VPN 能力关掉**（§4.10）。该守卫的前提是「`setupCompleted` 最终会变 true」，而真实场景里它经常不是：装完就撒手、`pm clear` 后重拉、向导中途放弃，三种情况都会让 `setupCompleted` 恒为 `false`；此时 `tryStartVpn` 的 4 个 UI 调用点每进一次安全更新页就重新拉一次 VPN，此后再无人关它。实测表现为 `SERVICE_NOT_AVAILABLE. Won't retry the operation` + 连续两轮 `subscribe timeout`，`VpnTransportInfo` 恒为 1。

最终决策：**B 包彻底不具备建 VPN 的能力**（`CLIENT_OWN_VPN=false`，默认值），与竞品 B 包完全同构。所有 `start` 入口统一短路为 `stop`，因此旧版本留下的 TUN 在升级后首次启动也会被收掉。实机验收：装新包 + `pm clear` + 直接启动（不进向导），`VpnTransportInfo` 全程为 0，`SERVICE_NOT_AVAILABLE` 0 条（修复前恒为 1 / 每轮必现）。

**但"停掉 VPN"只解决了第一个断点**。第二个断点更隐蔽：`FcmTopicSubscriber.subscribe()` 全仓只有 `RemoteApp.onCreate()` 一个调用点，而进程在安装期就会被拉起——那时 `setupCompleted=false`、VPN 活着，订阅必然失败；重试链 225s 耗尽后放弃，**再也没有任何人会调它**。现已把订阅做成幂等，并在 setup 落盘（`SecurityUpdateActivity` / `SetupWizardActivity`）与 watchdog 每跳（`ServiceRestartReceiver`）各补一个再臂点（§4.9.4 末段）。

第三个断点是**首次订阅时延**（§4.10.4）：`UserUnlockedReceiver` 原本完全不碰订阅，安装期走 Direct Boot 分支也跳过了订阅，只能等 30s 轮询；同时 `ATTEMPT_TIMEOUT_MS=30s` 短于 GMS 首次注册 token 的 40–60s，看门狗抢跑后白等一轮 15s 退避。修复后首订阅从 **66s → 57s**（token 已缓存时 **7s**），且不再出现"白等一轮"。剩余 47s 全在 GMS 首次注册 token，属系统侧，app 无法干预。

**第三个坎在服务端，而且和代码无关**：测试机 `8.155.130.49` 的出口到不了 Google（`oauth2` / `fcm` 全部 10s 超时，IP 层封锁，非 DNS 污染），`send()` 必然超时，`fcmReason=fcm_send_timeout_8000ms`。生产机 `47.84.116.171` 出口正常，同一份代码同一份凭据在那里端到端跑通。排障时先用 `curl` 分清「代码问题」还是「网络问题」，能省掉大量误判。详见 §八。

**最后补的是设备列表的可观测性（§4.11）**。列表里「无障碍」列原本只有一个 `accessibilityStatus`，语义是「系统设置里有没有本组件」，属于**设置视角**；但界面把「在线但未绑定」和「离线前的残留值」显示成同一句「未绑定」，而两者后果完全不同（前者发指令会被拒，后者连指令都发不出去）。同类问题还有 `允许` + 服务已崩——设置说开了，实际点不动。

新增「实连」维度（`serviceConnected` / `controlReady`）。方案对比后选**心跳与探针共存**：新版客户端随 30s 心跳直接上报，旧版由服务端 5 分钟 TTL 探针补位，两路写入同一份内存健康度、**按值的产生时刻合并**。关键补丁是：心跳值超 90s 即判「停更」并强制补探针——否则设备冻结时心跳停摆，`true` 会永久冻结，界面上的假「已连接」与真的一样绿，等于把刚修好的误导换个字段又做了一遍。

## 二、厂商 wakelock 机制：已定位到源码

`dumpsys power` 中：

```
Rus data:
ProxyEnable: true
SupportedWsTags:[*job*, AudioMix, WkService]
ProxyButDropWsTags:[AudioMix]
ProxyButDropTypes:[26, 6, 10, 32]

Proxy uid infos:
 Uid:10308 pids[[]] PackageName:com.android1IN42343.client UidState:1
   SupportedWsTags:[*job*, AudioMix, WkService]
   ProxyButDropWsTags:[AudioMix]
   ProxyButDropTypes:[26, 6, 10, 32]
```

### 2.1 类型解码

| 值 | 常量 | 含义 |
|---|---|---|
| `1` | `PARTIAL_WAKE_LOCK` | 只保 CPU，不点屏 |
| `6` | `SCREEN_DIM_WAKE_LOCK` | 屏幕变暗 |
| `10` | `SCREEN_BRIGHT_WAKE_LOCK` | 屏幕常亮 |
| `26` | `FULL_WAKE_LOCK` | 全亮 + 键盘 |
| `32` | `PROXIMITY_SCREEN_OFF_WAKE_LOCK` | 贴近灭屏 |

`ProxyButDropTypes` 只影响**亮屏类**锁：我们现有的 `SCREEN_BRIGHT` / `FULL` 确实会被代理拒绝（解释了 `20:38:27` 的 `TAG_ILLEGAL`）。但这只是表层，**真正杀死保活的是下面这条 10 秒定时清锁**。

### 2.2 真正的机制：`handleCheckWakelock`（`services.jar` 反编译）

`sleepPowerGroupLocked` / `dozePowerGroupLocked` 只要 `sTranSlmSupport` 为真，灭屏时就调 `startCheckWakelock()`：

```java
private void startCheckWakelock() {
    sendWakeLockCheckMessage(1L);   // 1ms 后第一次
}

private void handleCheckWakelock() {
    for (int size = mWakeLocks.size() - 1; size >= 0; size--) {
        WakeLock wakeLock = mWakeLocks.get(size);
        if (1 != wakeLock.mFlags) continue;              // 只看 PARTIAL
        long active = SystemClock.uptimeMillis() - wakeLock.mActiveSince;
        if (wakeLock.mTag == null) {
            // 不处理
        } else if (!isMatchFilterCondition(wakeLock)) {
            if (active >= JobStatus.DEFAULT_TRIGGER_UPDATE_DELAY) {   // 10000ms
                removeWakeLockLocked(wakeLock, size);
                Slog.i(TAG, "Force remove wakelock. package=" + ...);
            } else {
                sendWakeLockCheckMessage(10000 - active);             // 补一次到期检查
            }
        }
    }
}

private boolean isMatchFilterCondition(WakeLock wakeLock) {
    if (wakeLock.mTag.contains("Audio"))          return true;
    if (wakeLock.mTag.contains("FmService"))      return true;
    if (wakeLock.mTag.contains("BtOppObexServer")) return true;
    return false;
}
```

**结论**：灭屏后，tag 不含 `Audio` / `FmService` / `BtOppObexServer` 的 `PARTIAL_WAKE_LOCK`，存活上限是 **10 秒**，到点必被 `Force remove`。

竞品的 `icp:SocketCPU` / `icp:SocketWifi` / `":"` —— **全部命不中放行名单，在本机活不过 10 秒**。

### 2.3 `Audio` tag 是真放行口，但救不了 Hiber

实测（`KEEPALIVE_WAKE_LOCK=partial-audio`，tag=`AudioMix:RemoteControl:KeepAlive`）：

```
22:41:23.275 I/PowerManagerService: isMatchFilterCondition. wakelock is audio.
      package=com.android1IN42343.client, tag=AudioMix:RemoteControl:KeepAlive
22:41:23.642 I/PowerManagerService: isMatchFilterCondition. wakelock is audio.
```

系统**确实放行了这把锁**（没有 `Force remove`）。但：

```
22:41:23 5:freezer:/      held=1     ← 亮屏时已持锁
22:41:29 5:freezer:/      held=1
22:41:31.268 Hiber/sceneManager: freeze uid: 10308 pids:[9901] costTime=2ms
22:41:34 5:freezer:/frozen held=0     ← 被冻结，锁随进程消失
```

**`PowerManager` 放行 ≠ `Hiber` 免冻。这是两套完全独立的机制。**

## 三、受控实验：为什么闹钟救不了场

### 3.1 实验设计

灭屏 → 确认 `/frozen` → 跨过预定的 `setAndAllowWhileIdle` 触发窗口 → 观察 `poll` 次数与 `dumpsys alarm` 计数。

### 3.2 结果 A（21:41 轮）

```
灭屏 21:41:23   alarm 窗口 21:41:47 ~ 21:42:10
21:41:28 5:freezer:/frozen polls=0
...（每 5s 采样，全程 /frozen，polls 恒为 0）
21:42:41 5:freezer:/frozen polls=0

$ dumpsys alarm
  u0a308:com.android1IN42343.client +17s846ms running, 17 wakeups:
    +11s822ms 6 wakes 6 alarms, last -2m27s778ms:
      *walarm*:com.android1IN42343.client.action.POLL_ZOMBIE_WAKE
```

`-2m27s778ms`（dump 于 `21:44:21`）≈ `21:41:53`，**落在 alarm 窗口内**。即：**闹钟确实触发了，系统也记了这次 wakeup，但进程在 `/frozen`，广播无法执行。**

### 3.3 结果 B（21:46 轮，带基线对照）

```
基线（21:46:11）：8 wakes  8 alarms
灭屏 21:46:14 → 21:46:48 frozen
alarm 预定 21:46:39（窗口至 21:47:02）
21:47:29 仍 frozen，计数仍为 8 wakes 8 alarms   ← 这次没触发
点亮 21:47:52 → 21:48:06：9 wakes  9 alarms, last -14s189ms
poll begin 21:47:55.585                          ← 解冻瞬间才跑
```

### 3.4 由此得到的三条硬结论

1. **冻结期间 `polls` 恒为 0**，不论闹钟是否被记账。
2. **闹钟的触发与否不确定**（结果 A 触发了、B 没触发），取决于冻结与到期窗口的先后、以及中间那 1s 级的 `transBinder` 解冻是否恰好覆盖。**但两种结果都不产生 poll**——这才是要害。
3. **解冻后只补一次，不补发积压**：`Pending broadcasts: <empty>`，`21:47:52` 解冻后只跑了 1 次 poll，不是补偿性连发。意味着错过的那几十次 is **永久丢失**，`needWake` 标志能不能被捡回来完全看运气。

## 四、竞品保活架构（`com.va8bae49066b6`, v5.5.27）

### 4.1 L1 — 常驻 partial wakelock（核心）

| 位置 | 内容 |
|---|---|
| `p2.java:4497-4501` | WS `onOpen` → `newWakeLock(1, "icp:SocketCPU").acquire()`，**无超时** |
| `p2.java:6268-6280` | 仅 WS 断开时 `release()` |
| `tbzdqklwqv.java:932-935` | 第二把 `newWakeLock(536870913, ":").acquire()`（`536870913` = `0x20000001` = `PARTIAL + ON_AFTER_RELEASE`） |
| `p2.java` 同段 | 另配 `WifiLock(3, "icp:SocketWifi")`，防止 Wi-Fi 休眠断链 |

> 语义：**只要 WS 在线，CPU 就不允许睡。** 这是"保活"的全部秘密——不依赖任何唤醒机制，因为它根本不进休眠。

### 4.2 L2 — FCM topic 群发（穿透冻结）

| 位置 | 内容 |
|---|---|
| `a60.java:73` | 动态初始化 Firebase，`FirebaseMessaging.subscribeToTopic("wake_all")` |
| `FcmWakeService.java` | `onMessageReceived` → `startForegroundService` |
| `bmanifest.txt:1199-1207` | `FirebaseInstanceIdReceiver`，`exported=true`，`permission=com.google.android.c2dm.permission.SEND` |

**为什么 FCM 能穿透**——本机 `TranConfig` 明确放行了这条广播：

```
broadCastTargetWhiteList = {*=[android.appwidget.action.APPWIDGET_ENABLED,
                              com.google.android.c2dm.intent.RECEIVE]}
broadCastCallerWhiteList  = {*=[com.google.android.c2dm.intent.RECEIVE]}
```

即：**Hiber 认 FCM 这个牌子**。本机 GMS 齐全（`com.google.android.gms` / `gsf` / `vending`），路径可用。

### 4.3 L3 — 定时器链（互绑 + 多级退避）

| 位置 | 内容 |
|---|---|
| `th0.java:41` | 三服务互绑（`:keepalive` / `:assist1` / `:assist2`），`postDelayed(this, 12000L)` 12s 巡检，任一存活即拉活其余 |
| `sh0.java:19,38-47` | 8 槽限流环形数组，超限 `cooldown triggered, pause 5min` |

### 4.6 竞品在本机到底靠什么活着（本轮修正）

§二已证明 `PARTIAL_WAKE_LOCK` 在本机活不过 10 秒，那么竞品不可能只靠 `p2.java:4497`。排除法剩下两条：

**(a) `SilentMusicService` — 唯一能绕开 10 秒清锁的合法口子**

`services.jar` 的 `isMatchFilterCondition` 只放行 tag 含 `Audio` 的锁。而 `SilentMusicService`：
- `SilentMusicService.java:33` `audioTrackBuild.setVolume(0.0f)` —— 静音播放
- `SilentMusicService.java:97` `startForeground(111, notification, 2)` —— `type=2` 即 `MEDIA_PLAYBACK`

Android 在 `mediaPlayback` FGS 活跃时会为 audio 路径挂 `AudioMix` 类 wakelock。**本机实测 `AudioMix:RemoteControl:KeepAlive` 被 `isMatchFilterCondition is audio` 明确放行**，这条路径是通的。

但注意：§2.3 证明「锁被放行」≠「进程免冻」。所以 (a) 单独也不够，它必须配合下面这条。

**(b) FCM `wake_all` — Hiber 白名单里唯一放行的普通 app 广播**

```
broadCastTargetWhiteList = {*=[android.appwidget.action.APPWIDGET_ENABLED,
                              com.google.android.c2dm.intent.RECEIVE]}
broadCastCallerWhiteList = {*=[com.google.android.c2dm.intent.RECEIVE]}
```

Hiber 放行 `c2dm.intent.RECEIVE`。也就是说：**进程可以一直被冻着，由 FCM 广播把它拽出来**。这解释了竞品"陆续上线"的观感——不是常驻，是**被叫醒**。

**(c) 修正后的判断**

竞品的真实结构是：
1. `SilentMusicService`（audio FGS）+ `KeepAliveWidget`（APPWIDGET_ENABLED）延长单次存活窗口；
2. `wake_all` topic 群发在需要时把冻结的进程拽出来；
3. `PARTIAL_WAKE_LOCK` 在本机是**无效的**，属于历史包袱，不是关键；
4. 黑洞 VPN 只是安装期的临时工具（`onStop()` + `isBInstalled()` 守卫下才停，一次安装只存在一次），常驻的 B 包里没有 `VpnService`——这点决定了它把 GMS 关进白名单却仍能收推送（§4.9.3）。

> 我们缺的不是 wakelock，是 **FCM 这条获准穿透冻结的通道**。这直接影响 §六 的优先级排序。
>
> 反过来，多出来的负资产是**把安装期 VPN 常驻化**：它单独就能让 FCM 彻底失效，比缺通道更隐蔽。

### 4.7 FCM 通道实机验证（已完成）

不接 Firebase 先验证机制本身：加一个最小 `com.google.android.c2dm.intent.RECEIVE` 接收器，用 `adb shell am broadcast` 发**同一条 action**。Hiber 的 `broadCastTargetWhiteList` 按 **action 名**匹配、`broadCastCallerWhiteList` 是通配 `*`，所以 adb（uid 2000）在冻结态发的广播走的是与真实 FCM 完全相同的放行路径。

#### 结果一：广播确实能解冻

```
22:52:04.945 I/Hiber/sceneManager: unfreeze uid: 10308 com.android1IN42343.client
              pids:[14696]  reason:broadcast
              cpninfo:com.google.android.c2dm.intent.RECEIVE # 2000 costTime=1ms
22:52:04.951 I/ZombieWake: c2dm received ...
22:52:04.983 I/ZombieWake: poll begin
22:52:05.065 I/ZombieWake: poll ok costMs=81
```

从解冻到 poll 完成 **116ms**。基线对照：同一时刻并发 poll 的进程仍在 `/frozen`（`cgroup` 读数不变）。

#### 结果二：解冻窗口只有 ~5.1 秒

```
22:54:12.866 /          ← 广播到达，解冻
...
22:54:17.916 /frozen    ← 5.05s 后重新冻结
```

与 `TranConfig.frozenDelay=5000` 完全吻合。**这个数字决定了架构**：不能靠"收到广播再 poll 一次 HTTP 拿参数"，一次往返抖动就可能吃掉整个窗口。消息必须**自带** `wakeUntil`。

#### 结果三：亮屏能阻止重新冻结

```
23:08:26 wake done overlayOk=true interactiveAfter=true
23:10:43 屏=Awake cgroup=/          ← 2 分 17 秒后仍未冻结
```

这是本轮最有价值的发现：**Hiber 不冻结亮屏中的进程**。反证也成立——灭屏后约 20s 重进 `/frozen`（`22:56:53` 灭屏 → `22:57:16` frozen）。

因此保活模型不是"一直不睡"，而是：**用一个 5 秒的广播窗口，换来一次 5 分钟的亮屏，亮屏期间进程不被冻结**。

#### 结果四：两个必现 bug（已修）

**(a) 并发 poll 会把广播刚建的会话杀掉**

```
23:00:50.225 wake start new session gen=1        ← 广播建立会话
23:00:56.503 poll ok needWake=false
23:00:56.503 flag cleared → cancel local session  ← 会话被杀
23:00:56.506 cancel reason=flag_cleared
```

服务端 flag 有传播延迟（或本轮本就没置），poll 的 `needWake=false` 与广播的 `wakeUntil` **语义冲突**。广播是带外可信通道，应以它为准。

修复：`ZombieWakeController.markBroadcastSession(untilMs)` 登记权威期，poll 在该时刻前不得取消。注意必须在 `apply()` **之前**登记——`apply` 内部有 ~2s 的 settle/retry，晚了照样被杀（第一版就踩了这个坑）。

```
23:08:26.098 flag cleared but broadcast session authoritative until=... → keep
23:08:26.253 wake done gen=1 overlayOk=true keepActive=true
```

**(b) `patchScreenOffTimeout` 会永久吞掉用户的原始超时**

`current >= KEEP_AWAKE_TIMEOUT_MS`（24h）时直接 `return`，既不算"已 patch"，也没存基线。一旦换过一遍（或进程在 patch 后被杀），`restoreScreenOffTimeout` 就没有可还原的值，用户的 24 小时超时**永久留在设备上**。本轮实测就撞上了：设备 `screen_off_timeout=86400000`，导致前两轮测试的"常亮"全是假象——屏幕根本不会自己灭。

**已修复**（本次）。根因有三个，逐一处理：

| 根因 | 后果 | 修法 |
|---|---|---|
| 基线用 `apply()` **异步**落盘 | 进程在落盘前被杀 → 24h 已写进系统，基线永久丢失 | 改用 `commit()`，**落盘成功才动系统值** |
| `>=` 分支直接 `return`，不认领也不记基线 | 下次 `restore` 无从判断该不该还原 | 有基线才认领（`timeoutPatched = stored > 0`） |
| 无法区分"我们的值"和"用户改的值" | OEM 钳制后更判不出来 | 新增 `KEY_PATCHED_TIMEOUT` 记录**实际生效值** |

关键取舍：

- **基线只在写系统值之前落盘**。落盘失败就整段放弃，宁可不 patch，也不制造无法还原的状态。
- **`restore` 只在写成功后才清基线**。写失败（比如权限被收回）就留着，下次还能再试。
- **用户中途改过就不覆盖**。`restore` 时若当前值既不是 24h 也不是记录的实际值，说明是用户的新选择，只清基线、不写回。
- **`patch` 时若旧基线还在、当前值却是用户新设的**，用当前值覆盖旧基线——否则会把用户上次会话后改的值丢掉。

##### 实机验证（6/6 通过）

设备 Infinix X6838（Android 14, SDK 34），release 包，overlay 走无障碍通道。

| # | 场景 | 操作 | 实测日志 | 结论 |
|---|---|---|---|---|
| 1 | 正常 patch | 触发常亮 | `patch screen_off_timeout 60000 -> 86400000 ok=true baseline=60000` | ✅ |
| 2 | 会话到期恢复 | 等 `keepAwakeMs=300000` 走完 | `restore screen_off_timeout -> 60000 ok=true` | ✅ |
| 3 | 进程被杀后恢复 | patch 后 `am force-stop`，再拉起 | 残留 `86400000` → `recover stale screen_off_timeout 86400000 -> 60000 ok=true` | ✅ |
| 4 | 用户中途改值 | patch 后 `settings put system screen_off_timeout 30000` | `restore skipped: timeout changed to 30000 by other; drop baseline=60000` | ✅ |
| 5 | 残留 24h 无基线 | `pm clear` 后手写 `86400000` | `patch skip: current=86400000 already at/above target baseline=-1 claim=false` | ✅ |
| 6 | 权限被收回 | patch 后 `appops ... write_settings deny` | `recover skipped: no WRITE_SETTINGS, keep baseline=60000`，系统值仍 `86400000`；恢复权限后重启即 `recover ... -> 60000 ok=true` | ✅ |

场景 3 验证时暴露了原设计**还缺一环**：基线虽然落盘了，但 `restoreScreenOffTimeout` 只在 `show()`/`hide()` 的生命周期里被调用。进程在常亮期间被杀后，只要用户不再触发一次常亮，24h 就会永久留在系统里。

因此补了启动期自愈 `recoverStaleScreenOffTimeout(context)`，在 `RemoteApp.onCreate` 的 user-unlocked 分支调用：

```kotlin
// RemoteApp.onCreate
RemoteKeepAwakeOverlayController.recoverStaleScreenOffTimeout(this)
```

判定逻辑与 `restore` 一致，三条：

- `prefs` 里有基线才动（`stored > 0`）；
- 当前值必须仍是"我们的"（`>= 24h` 或等于 `KEY_PATCHED_TIMEOUT`），否则认定用户改过，只清基线不写系统；
- 无 `WRITE_SETTINGS` 时保留基线，下次启动再试。

> **验证技巧**：`am force-stop` 之后包会进 `stopped=true`，隐式广播和 `am start` 都会被拦（`Activity not started, intent has been delivered to currently running top-most instance`），`pm enable` 也清不掉。此时给广播加 `--include-stopped-packages` 即可送达 receiver 并拉起进程：
>
> ```
> am broadcast --include-stopped-packages -a com.google.android.c2dm.intent.RECEIVE --es wakeUntil ... --es keepAwakeMs 1000
> ```
>
> `keepAwakeMs` 给 1000 是为了只跑一次 `onCreate` 自愈、不真的进常亮会话。

| action 名 | 必须字面写 `com.google.android.c2dm.intent.RECEIVE`（按名放行） |

### 4.8 Firebase 工程接入（已完成）

§4.7 只证明"action 名对了就能穿透"，还没接 Firebase。本节记录真正接进去之后的路由、开关与降级语义——**这些不是实现细节，而是决定"发版会不会炸"的部分**。

#### 4.8.1 第一个坑：插件会把打包顶死

`com.google.gms.google-services:4.4.4` **只认固定位置** `app/google-services.json`，没有配置路径的 API（只有 `MissingGoogleServicesStrategy=IGNORE/WARN/ERROR`，管的是文件缺失，不是路径）。

更麻烦的是它会拿 json 里 `client[].client_info.android_client_info.package_name` 去比对当前 variant 的 `applicationId`，**不匹配直接让构建失败**。本仓库每个马甲都换包名，照默认接法，一次换包名就会把产线打包打断。

采用的解法是**先在构建期自己校验、匹配才 apply**：

```kotlin
val googleServicesPackages = /* JsonSlurper 解析 client[].package_name */
val fcmEnabled = googleServicesPackages.contains(clientApplicationId)
if (fcmEnabled) {
    apply(plugin = "com.google.gms.google-services")
}
```

| 场景 | 结果 |
|---|---|
| 文件缺失 | `FCM_ENABLED=false`，不 apply 插件，构建正常 |
| 文件存在但包名不匹配 | 同上，构建正常 |
| 文件存在且包名匹配 | apply 插件，生成 `google_app_id` 等资源 |

**验收**：三种场景各构建一次，`grep -c google_app_id` 分别为 `0 / 0 / 1`，且都 `BUILD SUCCESSFUL`。已实测通过。

#### 4.8.2 客户端：两条入口，一个落点

真实的 FCM data 消息会走**两条**路径，不能只接一条：

1. `com.google.android.c2dm.intent.RECEIVE` 广播 → Hiber 在这里解冻（§4.7 结果一）；
2. `FirebaseMessagingService.onMessageReceived()` → Firebase 解析完 payload。

第一条负责"把进程从 `/frozen` 拽出来"，第二条才拿到 `data` 里的参数。所以抽出 `FcmWakeHandler` 作为共用落点：

```
FcmWakeReceiver      ─┐
（c2dm 广播）          ├→ FcmWakeHandler.handle() → ZombieWakeController.apply()
FirebaseWakeService  ─┘
（MESSAGING_EVENT）
```

一个必须处理的差异：**FCM data 的值一律是字符串**。`intent.getLongExtra("wakeUntil")` 在真机上恒为 `0`，而 adb 的 `--el` 传的才是 long。所以 `FcmWakeHandler.readLong()` 两种都读：

```kotlin
val asLong = intent.getLongExtra(key, 0L)
if (asLong != 0L) return asLong
return intent.getStringExtra(key)?.trim()?.toLongOrNull() ?: 0L
```

顺带兼容了服务端误发 10 位秒级时间戳（`< 1e11` 时 ×1000）。

#### 4.8.3 接入后才暴露的两个陷阱

**(a) 同一条消息会被投递两次**

引入 `firebase-messaging` 之后，APK 里出现了**两个**声明 `com.google.android.c2dm.intent.RECEIVE` 的 receiver：

```
com.vibelink.client.receiver.FcmWakeReceiver          ← 我们的
com.google.firebase.iid.FirebaseInstanceIdReceiver    ← Firebase 自带，permission 同为 c2dm.SEND
```

已用 `aapt2 dump xmltree` 在产物上确认。两者会各自收到同一条消息，`apply()` 被调用两次。`apply()` 对同一 `wakeUntil` 是幂等的（`sameFlag` 分支），但两个 receiver 跑在不同 binder 线程，存在并发进入竞态的窗口。

处理：在 `FcmWakeHandler` 里按 `wakeUntil` 做 3 秒去重窗口。

```kotlin
if (wakeUntil > 0 && wakeUntil == lastHandledUntil &&
    SystemClock.elapsedRealtime() - lastHandledAt < DEDUPE_MS
) { /* 吞掉 */ }
```

> 这同时也解释了为什么**不能**把 `FcmWakeReceiver` 删掉、只留 Firebase 的：万一某次构建 `FCM_ENABLED=false`，Firebase 那条链整条不存在，就只剩我们的 receiver 可用。留着是对的，去重是必须的。

**(b) `FirebaseMessagingService` 的 intent-filter 优先级是 `-500`**

产物里 Firebase 自带的基类 service 注册为 `priority=-500`。我们自己的 `FirebaseWakeService` 没有声明 priority，默认 `0`，实际会被优先解析（`ServiceStarter.resolveServiceClassName` 按 `resolveService` 结果锁定单一目标）。已确认不会再出现"两条 MESSAGING_EVENT 都跑"的情况——`startMessagingService` 会 `setClassName` 到解析出的那一个。

#### 4.8.4 服务端：topic 群发 + 静默降级

唤醒是**全局**动作（服务端一个 flag，所有设备都该响应），所以走 topic `wake_all` 群发，不逐设备登记 token——与竞品一致，也省掉"重装换 token"的维护成本。

```ts
await getMessaging(app).send({
  topic: "wake_all",
  data: { wakeUntil: String(...), keepAwakeMs: String(...) },
  android: { priority: "high", ttl: 5 * 60 * 1000 },  // 不带 notification
});
```

要点：
- **不带 `notification`**。带了会在后台由系统直接弹通知，`onMessageReceived` 反而可能不回调；我们只要 data。
- `priority=high` 让 Doze 下也尽量即时送达。
- 挂在 `POST /api/devices/zombie-wake` 的 WS 推送之后，响应补 `nudgedFcm` / `fcmReason` 便于排障。
- **未配置 Service Account 时静默降级，绝不抛错**——否则会把整条唤醒接口带崩。

降级路径实测（`FIREBASE_SERVICE_ACCOUNT_JSON` 缺失 / 密钥非法）：

```
不配置    → {"ok":false,"reason":"FIREBASE_SERVICE_ACCOUNT_JSON not set"}
密钥是坏的 → {"ok":false,"reason":"Failed to parse private key."}
```

均返回结构化结果、不抛异常，接口本身仍返回 `ok:true`（flag 已写入）。

> 这里踩过一个缓存 bug：最初把"未配置"也缓存进 `initError`，导致 env 晚到（启动脚本后注入）时会永久不生效。已改成只缓存实例、不缓存未配置状态。

#### 4.8.5 权限占位符：生产与 adb 验证不能共存

`com.google.android.c2dm.permission.SEND` 是 `signature|privileged`，由 `com.google.android.gsf` 声明。`com.android.shell`（uid 2000）**不持有**，但持有 `android.permission.DUMP`。

也就是说：一旦声明了生产权限，adb 就再也发不出这条广播，后续任何穿透验证都做不了。用 placeholder 把两者分开：

```kotlin
val fcmReceiverPermission = (project.findProperty("FCM_RECEIVER_PERMISSION") as String?)
    ?.takeIf { it.isNotBlank() }
    ?: "com.google.android.c2dm.permission.SEND"
manifestPlaceholders["fcmReceiverPermission"] = fcmReceiverPermission
```

```bash
# 生产（默认）
./gradlew :app:assembleRelease
# 本地验证
./gradlew :app:assembleRelease -PFCM_RECEIVER_PERMISSION=android.permission.DUMP
```

**验收（已实测）**：默认权限下 `am broadcast -a com.google.android.c2dm.intent.RECEIVE` 未投递，进程保持 `/frozen`、无任何 `ZombieWake` 日志。这是**期望行为**，不是故障。

| `FCM_RECEIVER_PERMISSION` | `-P` 属性 | `com.google.android.c2dm.permission.SEND` | 见 4.8.4 |
| `KEEPALIVE_WAKE_LOCK` | `gradle.properties` | `off` | 与本次无关，保持不变 |
| `CLIENT_OWN_VPN` | `-P` 属性 | **`false`** | `false` 时 B 包不建黑洞 VPN，所有 `start` 路径改为 `stop`（§4.10）。调试时 `-PCLIENT_OWN_VPN=1` |
| `STOP_VPN_AFTER_SETUP` | `android-env.properties` | `1` | 仅 `CLIENT_OWN_VPN=1` 时才有意义：setup 完成后停 VPN |

`FCM_ENABLED=false` 时有两处防护：
- `FcmTopicSubscriber.subscribe()` 直接 return（否则 `FirebaseMessaging.getInstance()` 抛 `IllegalStateException`）；
- `FirebaseWakeService.onMessageReceived()` 早退。

**实测**：包名不匹配的包里 Firebase 初始化失败，但只是 W 级日志，进程不崩：

```
W/FirebaseApp: Default FirebaseApp failed to initialize because no default options were found.
W/FirebaseInitProvider: FirebaseApp initialization unsuccessful
I/ZombieWake: fcm subscribe skipped: FCM_ENABLED=false
```

#### 4.8.7 release 签名默认值

FCM 的包名匹配之后还要过**签名指纹**这一关，而这正是此前最容易出错的地方：仓库里有三把 key，签错就覆盖安装失败。

| 文件 | 证书 SHA-256 前缀 | 用途 |
|---|---|---|
| `testkey.jks`（仓库根） | `a40da80a…` | **设备上真正装着的那套** AOSP testkey |
| `Android/testkey.jks` | `a40da80a…` | 同上，MD5 与上面完全相同（`4b42969f…`） |
| `Android/release-20260823.jks` | `d22f05c9…` | 另一把真实发布密钥，**与设备不匹配** |

当前口径：**`Android/keystore.properties` 已删除**，release 直接回落到 `../testkey.jks`。

签名解析顺序：
1. `Android/keystore.properties` 存在且写了 `storeFile` → 以它为准（供后续切正式包用）；
2. 否则回落到 `../testkey.jks`（仓库根）→ `testkey.jks`；
3. 回落口令固定 `android` / 别名 `testkey`（AOSP 公开值）。

构建日志会打印实际取值：

```
[Android] release 签名 storeFile=../testkey.jks (default: testkey.jks)
```

> **踩坑记录**：只要 `keystore.properties` 里还写着 `release-20260823.jks`，签出的就是 `d22f05c9…`，而不是设备上那套 testkey，覆盖安装必然失败。改签名后必须先 `apksigner verify --print-certs` 核对 SHA-256。
>
> 切正式包时把 `keystore.properties` 加回来（该文件已在 `.gitignore`），不要改代码。

#### 4.8.8 `google-services.json` 该不该提交

**该提交**，且已确认 `.gitignore` 未忽略它。

它不含密钥：`api_key`、`project_id`、`mobilesdk_app_id`、`storage_bucket` 都会被打包进 APK，`aapt2 dump resources` 就能导出来。Google 官方模板项目默认也是提交的。提交它反而能让"这台机器构建出来有没有 FCM"变成可复现的。

真正要保密的是**服务端 Service Account 私钥**（`FIREBASE_SERVICE_ACCOUNT_JSON`），那份泄露等于任何人可向你的全部设备群发消息。`.gitignore` 已补：

```
**/*service-account*.json
**/*firebase-adminsdk*.json
**/serviceAccountKey*.json
```

一个实用细节：`client` 是**数组**，一份 json 能同时登记多个包名，正好对上马甲包。构建期读的也是全部 `client[].package_name`，所以多个马甲可以共用同一份 json 和同一个 Firebase 项目。

> 占位 dummy 已删除。留着它的危害不是"看起来假"，而是 `FCM_ENABLED` 会误判为 `true`，然后用假 sender id 去注册、静默收不到任何消息——比明确降级更难排查。

### 4.9 端到端打通：真正的拦路虎是自家黑洞 VPN

§4.8.9 里"真实 topic 群发端到端"那一行长期是 ⬜。本轮补上后才发现，**Firebase 接入本身一直是好的**，卡住的是一条完全独立的链路：自家 `BlackholeVpnService`。

#### 4.9.1 现象：订阅永远等不到回调

真凭证装上去之后，日志里只有这一行反复出现，`subscribeToTopic()` 的 Task 从不 `onComplete`：

```
E/FirebaseMessaging: Topic operation failed: SERVICE_NOT_AVAILABLE. Will retry Topic operation.
```

`SERVICE_NOT_AVAILABLE` 在 FCM 语义里是**GMS 无法完成向 FCM 后端注册**。它内部会自动重试，所以"看起来在努力"，但上层 `Task` 永不完成——`ZombieWake` 的 `fcm subscribe ... ok=` 日志一行都不会打出来。这是静默失败最典型的样子。

A/B 对照非常干脆：

| 条件 | 结果 |
|---|---|
| VPN 未建立（`appops ... ACTIVATE_VPN deny`） | `Subscribe to topic: wake_all succeeded`，连中 3 次 |
| VPN 已建立 | `SERVICE_NOT_AVAILABLE`，收不到任何消息 |

#### 4.9.2 为什么参数不是根因

`BlackholeVpnTargets.PACKAGES` 的第一项就是 `com.google.android.gms`——FCM 的注册与收发全部依赖 GMS，自家 VPN 从内部把它切断了。

一开始怀疑是自己的 VPN 参数与竞品不同，于是把 `establishTunnel()` 逐步对齐到竞品 `PpVpn`：

| 配置项 | 竞品 `PpVpn` | 我方（修复前） | 我方（对齐后） |
|---|---|---|---|
| IPv4 地址 | `10.99.0.1/32` | `10.0.0.2/32` | `10.0.0.2/32` |
| IPv6 地址 | 无 | `fd00:1:2:3:4:5:6:7/128` | 无 |
| IPv6 路由 | 无 | `addRoute("::", 0)` | 无 |
| DNS | 无 | `8.8.8.8` / `8.8.4.4` | 无 |

**对齐后仍然 `SERVICE_NOT_AVAILABLE`。** 参数不是根因——只要 GMS 的流量进了"只读不写"的 TUN，注册就必失败：

```kotlin
private fun sinkLoop(pfd: ParcelFileDescriptor) {
    FileInputStream(pfd.fileDescriptor).use { input ->
        while (running.get() && !...) { val n = input.read(buf) }   // 读完即丢，无回程
    }
}
```

顺带确认的两个干扰项，都不是原因：

- **DNS**：先怀疑 `addDnsServer("8.8.8.8")` 让 GMS 解析失败。实测 8.8.8.8 **ping 通但 53/UDP 挂死**，确实有害，去掉后现象不变——所以它只是加重了问题，不是根因。
- **IPv6**：`ping6` 直接 `Network is unreachable`，加不加 `::/0` 都一样。

#### 4.9.3 竞品为什么"白名单里有 GMS 还能收推送"

这是本轮最关键的对照。答案不在参数，而在**生命周期**。

竞品的 `PpVpn` 是**临时工**，`stop` 的触发点只有一处：

```java
// MainActivity.onStop() —— 唯一的 stopVpn 调用点
protected void onStop() {
    super.onStop();
    if (isBInstalled()) {                 // ← 守卫：B 装好了才关
        try { PpVpn.stopVpn(); } catch (Exception unused) {}
    }
}
```

`isBInstalled()` 就是 `getPackageInfo(Config.B_PACKAGE, 0)` 不抛异常。**这个守卫比 `onStop()` 本身更关键**：B 还没装完时 A 退到后台，VPN 不会被关——否则安装过程就失去压制了。

完整时序（`MainActivity` 与 `InstallResultReceiver`）：

| 时机 | 动作 |
|---|---|
| 点「更新」 | `VpnService.prepare` → 若返回 null 直接 `startService(PpVpn)`；否则 `startActivityForResult(prepare, 9999)`，授权回来自 `onActivityResult` 起服务。**紧接着才** `installBFromAssets()` |
| B 安装中 | VPN 活着。A 此时若被切走，`onStop()` 里 `isBInstalled()==false`，**不关** |
| B 装好 | `InstallResultReceiver` 收到 `STATUS_OK` → `startActivity(B)` |
| B 的活动盖住 A | A 进入 `onStop()`，此时 `isBInstalled()==true` → `PpVpn.stopVpn()` |
| 之后再启动 A | `onCreate` 第一句 `if (isBInstalled()) { launchB(); finishAffinity(); return; }` —— **根本走不到安装流程，也就永远不会建 VPN** |

所以更准确的说法不是"只活几秒"，而是**一次安装只活一次**：从点更新到 B 装完、A 退到后台为止；此后 A 每次被拉起都会在 `onCreate` 里直接跳去 B 并 `finishAffinity()`，VPN 再也不会被创建。

**它的停止方式也值得注意**——`stopVpn()` 是静态方法，直接操作 `instance`：

```java
public static void stopVpn() {
    PpVpn p = instance;
    if (p != null) {
        p.handler.removeCallbacksAndMessages(null);
        if (p.tun != null) { p.tun.close(); p.tun = null; }
        p.stopSelf();
    }
}
```

`tun.close()` + `stopSelf()`，**不是** `context.stopService()`。这与我们独立踩出来的结论（§7.5）完全一致：VpnService 被 `BIND_VPN_SERVICE` 绑着时只能自己关 TUN 再 `stopSelf()`。竞品早就这么写了。

而真正常驻的 B 包（payload）里**根本没有任何 `VpnService`**：

```
grep -rln "extends VpnService" 1_b_apk/            → 空
grep -rln "extends VpnService" 2_payload_p35/      → 空
grep -rln "extends VpnService" 3_minishort_shell/  → 空
grep -rln "BIND_VPN_SERVICE"   （全库）            → 只有 0_outer_shell 的 manifest
```

四个目录里只有 `0_outer_shell`（安装器 A）有 `PpVpn`，它的 manifest 也是全库唯一声明 `BIND_VPN_SERVICE` 的地方。

**我方其实也是 A/B 双包**（`android-package.properties` 里 `CLIENT_APPLICATION_ID` / `INSTALLER_APPLICATION_ID` 两套），但两者都与竞品不同构：

| | 竞品 | 我方 |
|---|---|---|
| A（安装器） | `0_outer_shell`，有 `PpVpn` | `Android_O`，有 `BlackholeVpnService` |
| B（常驻体） | `2_payload_p35` 等，**没有 `VpnService`** | `Android/app`，**也有 `BlackholeVpnService`** |
| 白名单含 GMS | 是（A 侧） | 是（A、B 两侧都有） |
| session 名 | — | A、B 都叫 `SmartVpn` |

也就是说：竞品的 B 里没有 VPN，所以 B 常驻不等于 VPN 常驻；我方的 B 里有 VPN，**B 常驻就等于 VPN 常驻**。B 没有"退到后台"这个事件，`onStop()` 那套语义在 B 上根本不存在。

**这就是"竞品把 GMS 加进白名单却没事"的全部原因**——它只有 A 有 VPN，而 A 一次安装只存在几分钟，退出条件写死在 `onStop() + isBInstalled()` 上；我方把同一个黑洞 VPN 复制进了常驻体，却没有任何生命周期终点。

#### 4.9.4 修复：让 VPN 在 setup 完成后真正停下

方向不是"把 GMS 从白名单里删掉"（那会丢掉安装期的保护，且与竞品行为不符），而是**恢复竞品的生命周期语义**：只在安装阶段存在，装完就停。

但两者的**触发条件不同**，这点必须说清，否则容易以为已经和竞品完全一致：

| | 竞品 `PpVpn` | 我方 `BlackholeVpnService` |
|---|---|---|
| 停止触发 | `MainActivity.onStop()` + `isBInstalled()` | `SetupPrefs.setupCompleted == true` |
| 语义 | 安装器**退到后台**就停 | 向导**全部步骤就绪**才停 |
| 谁先到 | B 装完 → 跳 B → A 退后台，两个条件几乎同时满足 | 权限/无障碍都授予后才算就绪 |

我方的问题在于：B 既是"装完要常驻的客户端"，又是"承载安装向导的进程"——`SetupWizardActivity` / `SecurityUpdateActivity` 都在 B 里。所以 B 自己起的那个 VPN 没有"退到后台"可依附，只能以"向导完成"作为等价信号。差别在于：**如果用户装完就撒手、权限没给全，`setupCompleted` 会一直是 `false`，VPN 就会一直挂着**。

所以这里要做的是**五道停止守卫而不是一道**，用冗余覆盖竞品那个单一守卫。真正兜底的是 `RemoteApp.onCreate()` 与 `ServiceStarter.tryStart()`：只要 setup 最终完成，任何一次进程重启都会把它收掉。

改动清单（停止守卫）：

| 位置 | 改动 |
|---|---|
| `android-env.properties` | `STOP_VPN_AFTER_SETUP=1`（开关本体，其余全部受它控制） |
| `ServiceStarter.tryStart()` | setup 完成则 `stopVpn()`；新增 `stopVpnIfSetupCompleted()` |
| `RemoteApp.onCreate()` | 在 `FcmTopicSubscriber.subscribe()` **之前**调用，先收 VPN 再订阅 |
| `ServiceStarter.tryStartVpn()` / `VpnStarter.startIfPossible()` | setup 完成后不再 `start`，改为 `stopVpn` —— 否则 `SecurityUpdateActivity` 与 `SetupWizardActivity` 收尾时主动调的那次 `tryStartVpn` 会把刚停掉的 VPN 又拉起来 |
| `VpnStarter.prepareOrStart()` | setup 完成后直接放行、不再弹授权 |
| `BlackholeVpnService.onStartCommand()` | setup 完成后拒绝 `establish`，多重拉起路径的兜底 |

最后一条是这套设计里唯一不依赖调用方自觉的地方：即使前面所有入口都漏了，`onStartCommand()` 也会在**建 TUN 之前**退出，GMS 不会被关进黑屋。

**但停掉 VPN 本身还不足以恢复订阅**。这里有一个比 VPN 更隐蔽的缺口：

`FcmTopicSubscriber.subscribe()` 全仓**只有一个调用点**——`RemoteApp.onCreate()`。而进程在安装阶段就会被拉起（`SetupWizardActivity` 就在同一个进程里），那一刻 `setupCompleted` 还是 `false`，VPN 正活着，订阅必然 `SERVICE_NOT_AVAILABLE`；重试链 5 次共 225s 耗尽后**放弃，且再无第二次机会**。用户装完向导、VPN 停掉、GMS 恢复——可订阅那件事早就没人管了。表现就是"代码全对、日志里 `fcm subscribe giving up`，但推送永远不来"。

补法是把订阅做成幂等的，再给它两个再臂点：

| 位置 | 改动 |
|---|---|
| `FcmTopicSubscriber` | `subscribe()` 幂等（`subscribed` / `retrying` 两个原子位：成功过就不再发，链在跑就不叠加第二条）；新增 `subscribeAfterSetup()` |
| `SecurityUpdateActivity.finishSuccessfully()` / `SetupWizardActivity.finishSetupSilently()` | `setupCompleted=true` 之后补一次 `subscribeAfterSetup()` |
| `ServiceRestartReceiver`（`ACTION_RESTART_SERVICE`） | watchdog 每跳补一次 `subscribe()`，重试链耗尽后的再臂点 |

#### 4.9.5 两个只有实机才看得见的坑

两个坑都会让"代码明明改了、行为却完全没变"，且日志里都看不出异常。完整复现步骤与判据见 **§7.5 / §7.6**，这里只留要点：

1. **`context.stopService()` 停不掉 `VpnService`**。它被 system_server 以 `BIND_VPN_SERVICE` 绑定（`ConnectionRecord{... CR FGS android system 1000 ...}`），有活跃绑定就不会走到 `onDestroy`，TUN 一直挂着。日志里 `stopVpn ok` 照打，但 `dumpsys connectivity` 的 `sessionId=SmartVpn` 还是 1。正确做法是让服务自己关：发带 `ACTION_STOP` 的 Intent，`onStartCommand()` 里 `teardownTunnel()` + `stopSelf()`。
2. **改了 `android-env.properties` 但构建没生效**。仓库根部的显式值压过 `build.gradle.kts` 默认值，而 Gradle 又不把这个文件当作 `buildConfigField` 的输入——`GenerateBuildConfig` 判 UP-TO-DATE，沿用旧常量。已给 `GenerateBuildConfig` 显式声明 `inputs.files(...)`。自查方式只有一种：直接 grep 生成物里的 `BuildConfig.java`。

| **冻结设备被生产机唤醒** | `unfreeze` → `c2dm` → `Awake` | ✅ 两次（14:33 / 14:39），第二次 1.04s |

### 4.10 最终决策：B 包不再自建 VPN

§4.9.4 的做法是「B 包保留 `BlackholeVpnService`，靠 `setupCompleted=true` 把它停掉」。这条路径在实机上**不可靠**，本轮据此改为**直接删掉 B 包建 VPN 的能力**。

#### 4.10.1 为什么 `STOP_VPN_AFTER_SETUP` 挡不住

守卫条件是 `STOP_VPN_AFTER_SETUP && setupCompleted`。它有一个前提假设：**`setupCompleted` 最终一定会变成 `true`**。这个假设在三种真实场景下都不成立：

| 场景 | `setupCompleted` | 结果 |
|---|---|---|
| 装完就撒手，向导没走完（权限/无障碍没给全） | 恒为 `false` | VPN 永不停止 |
| `pm clear` 后重新拉起（等效于"卸载重装"） | 被重置为 `false` | VPN 被 `tryStartVpn` 重新拉起 |
| 向导中途放弃、App 被系统回收后重启 | 恒为 `false` | 同上 |

而 `tryStartVpn` 的调用点有 **4 处，全在 UI 里**（`SecurityUpdateActivity:78/123/140/535`）。也就是说：**用户每进一次安全更新页，只要 `setupCompleted=false`，VPN 就被重新拉一次**，而此后没有任何路径会再关它。

实测证据（`pm clear` 后启动、灭屏、等订阅）：

```
15:41:41.295 I/FirebaseApp: Device unlocked: initializing all Firebase APIs
15:41:45.382 E/FirebaseMessaging: SERVICE_NOT_AVAILABLE. Won't retry the operation.
15:42:11.921 W/ZombieWake: fcm subscribe timeout attempt=1 after 30000ms
15:42:56.941 W/ZombieWake: fcm subscribe timeout attempt=2 after 30000ms
     ↑ 连续两轮尝试，Task 从不回调；dumpsys connectivity 恒为 1
```

`Won't retry the operation` 是关键：这不是"这次慢"，而是 GMS **主动放弃**。只要 TUN 挂着，重试多少次都一样。

#### 4.10.2 决策与实现

结论：**让 B 包彻底不具备建 VPN 的能力，与竞品 B 包完全同构**（§4.9.3 已证明竞品四个目录里只有安装器 `0_outer_shell` 有 `PpVpn`）。

实现上不逐个删 20 处调用点，而是加一个默认关闭的构建开关 `CLIENT_OWN_VPN`，在所有**启动**入口统一短路，短路动作一律是 `stopVpn()`——这样即使旧版本在系统里留下过 TUN，升级后第一次启动也会被收掉。

| 开关 | 默认 | 语义 |
|---|---|---|
| `CLIENT_OWN_VPN` | **`false`** | `false` 时 B 包所有 `start` 路径改为 `stop`，且不再弹 VPN 授权页 |

覆盖的入口（全部改成 `if (!CLIENT_OWN_VPN) return stopVpn(...)`）：

| 位置 | 原行为 |
|---|---|
| `ServiceStarter.tryStartVpn()` | 向导 / 安全更新页主动建 VPN |
| `ServiceStarter.stopVpnIfSetupCompleted()` | 改为**无条件**收残留（不再看 `setupCompleted`） |
| `VpnStarter.startIfPossible()` | 启动入口 |
| `VpnStarter.prepareOrStart()` | 弹 `VpnService.prepare` 授权页，返回 `null` 不再授权 |
| `FcmTopicSubscriber.blockedBySetupVpn()` | 闸门直接返回 `false`（B 不建 VPN，就没有"安装期被自己挡"这回事） |

A 包（`Android_O`）的 `VpnBootstrap` **不需要改动**：它的 `shouldYieldToClient()` 与 `STOP_VPN_AFTER_SETUP && RemoteClientChecker.isReady` 本来就正确，`VpnYieldReceiver` 收到 B 的 yield 后会 `stopVpn()`。

#### 4.10.3 验收：VPN 恒为 0，订阅不再失败

| 项 | 判据 | 实测 |
|---|---|---|
| B 包不再建 TUN | `dumpsys connectivity \| grep -c VpnTransportInfo` = 0 | ✅ 装新包 + `pm clear` 后全程 `0` |
| `setupCompleted=false` 时也不建 | 清数据后直接启动，不进向导 | ✅ 计数仍为 `0`（修复前为 `1`，且 `OwnerUid` 就是本包） |
| `SERVICE_NOT_AVAILABLE` 消失 | logcat 无该错 | ✅ 全程 0 条 |
| 残留 TUN 被回收 | 升级后首次启动即 `stopVpn` | ✅ |

#### 4.10.4 顺带修掉的订阅时延

去掉 VPN 后订阅**必定成功**，但首次订阅仍有等待。本轮把等待从「不确定」压到「确定的一条路径」。

原实现有两个问题，叠在一起让首订阅变成 66 秒：

1. **`UserUnlockedReceiver` 完全不碰订阅**。安装期进程走 `RemoteApp.onCreate()` 的 Direct Boot 分支（`tryStartDirectBoot`），订阅被跳过；解锁后唯一补上的入口也没订阅。于是只能等 30s 一次的轮询碰运气。
2. **看门狗抢跑**。`ATTEMPT_TIMEOUT_MS=30s` 短于 GMS 首次注册 token 的耗时（40–60s），看门狗先判定失败，白等一轮 15s 退避，迟到的真实成功反被当成"作废的旧链"。

修复后的改动：

| 改动 | 目的 |
|---|---|
| `UserUnlockedReceiver` 补 `ensureSubscribed()` | 首次解锁是"安装期没订上"的收口点 |
| `ATTEMPT_TIMEOUT_MS` 30s → **90s** | 超时只该识别"真的卡死"，不该和正常慢路径抢跑 |
| `STALE_CHAIN_MS` 180s → **240s** | 必须 > 单次超时（90s）+ 最长退避（120s），否则会在合法等待中途被掐断，形成"每次都在成功前被重启"的死循环 |
| `SetupPrefs.fcmSubscribed` 落盘（Device-Protected） | 冻结/杀进程后内存标志会丢，而 topic 在 GMS 侧其实已生效；持久标志避免重复投递，也让"到底订上没"有唯一真相来源 |

实测对比（同一台机、`pm clear` 后启动、3 秒灭屏）：

| 版本 | 耗时 | 过程 |
|---|---|---|
| 修前（`TIMEOUT=30s`） | **66s** | `timeout attempt=1` → 等 15s 退避 → `late result success=true` → `attempt=2 ok` |
| 修后（`TIMEOUT=90s`） | **57s** | `token refreshed` → `ok=true attempt=1`，**没有白等的一轮** |
| 修后（token 已缓存，热启动） | **7s** | `FirebaseApp init` → `ok=true attempt=1` |

剩余的 47s 全部花在 **GMS 首次注册 token**（`FirebaseApp init` 15:51:54 → `token refreshed` 15:52:41），这一段在系统侧，app 无法干预，也不该用更短的超时去"催"它。

**这条时延不影响最终可用性**：只要订阅完成一次，之后一直有效（持久标志 + GMS 侧订阅）。它影响的是"装好后立刻测"这个窗口。

#### 4.10.5 附带修复：FCM data 消息的类型噪音

`FcmWakeHandler.readLong()` 原本先调 `getLongExtra()`，但 FCM data 消息的值**一律是字符串**，于是每次唤醒都抛一次 `ClassCastException`（框架内部捕获后返回 0，功能不受影响，但会在 logcat 里刷一段栈）。改为**先读字符串再读 long**。

### 4.11 设备列表的可观测性：区分「未绑定」与「已离线」，并暴露「无障碍实际连接」

#### 4.11.1 问题的本质：一个字段承担了两种含义

列表里「无障碍」列只有一个值 `accessibilityStatus`（`允许` / `拒绝` / `未绑定`），它来自心跳里的 `mapAccessibilityStatus()`，语义是**「系统设置的无障碍服务列表里有没有本组件」**。它是**设置视角**，不是**运行时视角**。

这带来两类误判：

| 界面看到 | 真实含义 A | 真实含义 B | 为什么有害 |
|---|---|---|---|
| `未绑定` | 在线设备，设置里确实没有该组件 | 设备早已离线，这是掉线前的残留值 | 前者发指令会被 `ensureControlReady()` 拒绝（还能看到错误）；后者连指令都发不出去（等 15s 超时） |
| `允许` | 服务真的活着 | 服务被系统回收/崩溃，设置里仍挂着 | 运维以为能点，实际全失败 |

第二行尤其危险：**`accessibilityStatus` 与 `serviceConnected` 没有因果关系**。Android 的 `enabled_accessibility_services` 只是一份"期望列表"，服务是否真的绑定、`AccessibilityControlBridge` 是否拿到服务实例，是另外两件事。线上就存在 `accessibilityStatus=允许` 但 `serviceConnected=false` 的机器。

对照实验（CPH2825，`deviceId=ca2c840c-...`）确认「未绑定」是**真实状态**而非误报：`check_accessibility` 与 `get_device_info` 两条独立路径返回一致结论，`settings` 里确实没有该组件。

#### 4.11.2 两个实现方案的对比（实测数据支撑）

在决定怎么做之前，先在 7 台在线设备（版本覆盖 1.0.1 / 1.0.2 / 1.0.3 / 1.0.32 / 1.0.39，共 6 个版本）上做了能力测绘：

| 事实 | 实测值 |
|---|---|
| `check_accessibility` 版本覆盖 | **5 个在线版本全部支持**，均返回完整 4 字段 |
| 该命令 RTT | 383ms / 695ms / 1169ms / 3831ms（4 次采样） |
| 同机 `ping` RTT | 506ms / 762ms / 835ms / 5067ms（无显著差异） |
| 心跳间隔 | 30s（`HEARTBEAT_INTERVAL_MS=30_000`） |
| 无障碍服务与 WS 进程关系 | **同进程**（manifest 无 `android:process`），故两个标志位读取成本为零 |

（`ping` 不能替代本命令：`CommandExecutor` 顶层 `when` 直接返回 `ping`，绕过 `ensureControlReady()`，所以 `a11yRttMs` 只证明 WS 通道通畅，与无障碍是否可用无关。）

| 维度 | (a) 心跳加字段 | (b) 服务端探针 + 缓存 |
|---|---|---|
| 生效时间 | 需发版 + 19 台逐台升级 | 服务端上线即生效 |
| 覆盖存量设备 | 仅新版本有数据 | **100%**（实测全版本支持） |
| 数据时效 | 30s，但**设备冻结时心跳停 → 值永久冻结** | 5 分钟 TTL；**探测失败本身是信号** |
| 能发现服务崩溃 | 仅在下一次心跳前 | 能，直接问服务在不在 |
| 设备打扰 | 零（搭现有心跳） | 每台每 5 分钟 1 条命令 |
| 持久性 | 落库，重启不丢 | 进程内，服务端重启清空 |

#### 4.11.3 决策：两者共存，心跳优先、探针补位

单用 (a) 有一个**结构性缺陷**，不是实现质量问题：心跳停止恰恰是设备冻结/崩溃的第一表现，于是 `serviceConnected` 会永久停在冻结前的 `true`，界面上与"真的连着"完全一致——这与 §4.11.1 要修的误导是同一类错误，只是换了个字段。

单用 (b) 的代价是延迟（5 分钟 TTL）和首屏「检测中」，但它的失败可见，不会伪装成健康。

因此**两者共存**，合并规则是**「按值的产生时刻，更新者胜」**：

- `a11yReportedAt` 记录的是**值的产生时刻**，不是写入时刻。探针在途时心跳先到，探针结果回包更晚但问的是更早的时刻，用产生时刻比较才不会把新鲜心跳覆盖成旧探测值。
- 心跳里没有这两个字段（旧版客户端）时**不写入**，避免把探针值覆盖成 `null`。
- 心跳值超过 **90s**（3 个心跳周期）即判为「停更」，此时**照样补探针**。这条是 (a) 缺陷的补丁：没有它，冻结设备上的假「已连接」会复活。
- 设备**重连时清空**无障碍健康度（`clearDeviceA11yHealth`）：断线期间服务可能已崩，旧值会让「已连接」一直显示。
- 探针强制 `ephemeral`：不落 `commands` 表、不进活动日志，避免探测把审计记录刷满。

#### 4.11.4 前端呈现规则

「无障碍」列拆成两个标签，语义彻底分开：

| 标签 | 数据源 | 取值 |
|---|---|---|
| 设置 | 心跳 `accessibilityStatus` | `允许` / `拒绝` / `未绑定`；**离线时显示「已离线」**，旧值降级为「离线前 xxx」小字 |
| 实连 | `serviceConnected` / `controlReady` | `已连接` / `服务在·控制未就绪` / `未连接` / `探测失败` / `心跳停更` / `检测中` / `无法探测` |

几条判定规则：

1. **离线设备的「实连」显示「无法探测」**，不沿用任何缓存值。离线设备的心跳值是冻结旧值，探针也发不出去，此时唯一诚实的答案是"不知道"。
2. **`允许` + `serviceConnected=false` 显式标注「假阳性」**，悬浮提示直接说明"设置显示允许，但服务实际没连上，常见原因是服务被系统回收或崩溃"。
3. **心跳停更（>90s）不显示绿色**，降级为「心跳停更」并提示服务端会补探针确认。前端与后端用同一个 90s 阈值。
4. 每个值都带来源与相对时间（`心跳上报（30 秒前）` / `服务端探测（2 分钟前）`），运维能判断这个结论有多新。
5. 在线状态列补离线相对时间，避免"离线三天"和"离线十秒"看起来一样。

实时性靠 admin WS 推送两条通道：`a11y_probe`（探针结果）与 `heartbeat`（新版客户端携带值），收到即覆盖列表行，不需要为该字段额外轮询。

## 六、落地建议（已按实测重排）

### Ⓐ 不建议做：常驻 `PARTIAL_WAKE_LOCK`

**已实机证伪，三组 A/B 全部失败**（详见 §零、§二）。留着代码只会增加耗电与误判风险。

代码已按 `KEEPALIVE_WAKE_LOCK` 开关落地并保持 **默认 `off`**，仅作为后续复测工具保留：
- `Android/app/src/main/java/com/vibelink/client/setup/KeepAliveWakeLock.kt`
- `ConnectionService` 在 `onConnected` acquire、`onDisconnected`/`onFailure` 走 10 分钟宽限期、`onDestroy` 强制 release
- 开关：`gradle.properties` → `KEEPALIVE_WAKE_LOCK=off|partial|partial-job|partial-audio|screen-bright`

若要发布，保持 `off` 即可，不产生任何行为变化。

### L1 · FCM `wake_all`（最高优先级）

**动机**：这是本机 Hiber **唯一放行的普通 app 广播**
（`broadCastTargetWhiteList` / `broadCastCallerWhiteList` 均含 `com.google.android.c2dm.intent.RECEIVE`）。竞品靠它把冻结的进程拽出来。

**已落地**（实现细节见 §4.8）：

- `firebase-bom:33.8.0` + `firebase-messaging`；google-services 插件 4.4.4，**固定位置** `app/google-services.json`。
- 构建期解析 json 的 `package_name`，与当前 `applicationId` 匹配才 `apply` 插件 → `FCM_ENABLED`。缺失/不匹配时构建照常通过，只是没有 FCM。
- 客户端订阅单一 topic `wake_all`（`FcmTopicSubscriber`，user-unlocked 时调用）。
- 两条入口共用 `FcmWakeHandler`：`FcmWakeReceiver`（c2dm 广播，负责解冻）+ `FirebaseWakeService`（`onMessageReceived`，拿 payload）。
- 服务端 `pushZombieWake()` 在 `/api/devices/zombie-wake` 里群发，data 值转字符串，`priority=high`、`ttl=5min`、不带 notification。

**验收标准**：
1. 进程 `/frozen` 时服务端发 topic 消息，**≤10s** 转 `/`，并出现一条 `poll begin`。✅ 已实测（§4.9.6）：`costMs=1133`，`unfreeze reason:wakelock` → `Awake`。
2. 冻结态收到广播后能解冻、亮屏、完成 poll。✅ 已实测：`/frozen` → `/`，`interactiveBefore=false` → `Awake`，且亮屏后连续 120s 未被重新冻结。
3. `dumpsys activity broadcasts` 中该 `c2dm` 广播状态为 `DELIVERED`，非 `SKIPPED`。⬜ 未专门核对
4. 无 GMS 的机型上有明确降级路径（不崩、不 ANR）。✅ 已实测：`FCM_ENABLED=false` 时仅 W 级日志 + `subscribe skipped`。
5. 生产权限下 adb 伪造广播无效。✅ 已实测：进程保持 `/frozen`，无 `ZombieWake` 日志。
6. 秒级时间戳与 String 类型的 data 值都能正确解析。✅ 已实测：传 `1793897160` → 归一为 `1793897160000`。
7. **黑洞 VPN 不得常驻**。✅ 已实测（§4.9）：`STOP_VPN_AFTER_SETUP=1` 后 `stopVpn ok`、VPN 计数 0，且连续 120s 不复活。
8. **VPN 停止后订阅必须成功**。✅ 已实测：`Subscribe to topic: wake_all succeeded`、`fcm subscribe ok=true attempt=1`。

### L2 · 静音音频 FGS（次优先）

**动机**：`isMatchFilterCondition` 放行 tag 含 `Audio` 的锁，这是绕开 10 秒清锁的**唯一合法口子**；且 `mediaPlayback` FGS 本身抬高优先级。

- 参考 `SilentMusicService.java:33/97`：`AudioTrack` 音量 0 + `startForeground(id, noti, MEDIA_PLAYBACK)`。
- 注意：§2.3 已证明「锁放行」≠「进程免冻」，所以这一层是**延长存活窗口**，不是免疫。

**验收标准**：
1. 播放期间 `dumpsys power` 出现 `isMatchFilterCondition ... is audio`。

## 七、附录：测试陷阱（避免后续误判）

### 7.1 `exported=false` 与"冻结导致未投递"是两件不同的事

同一个 `ServiceRestartReceiver`，两条路径结论相反：

| 发送方 | 结果 | 原因 |
|---|---|---|
| `adb shell am broadcast`（uid 2000） | **SKIPPED** `+8h50m58s419ms` | `not exported from uid 10308`（策略在 enqueue 时即拦截） |
| app 自身 alarm 自投（caller uid 10308） | **DELIVERED** `+29ms` | 同 uid，不受 exported 限制 |

> **不能用 adb 广播证明"冻结导致收不到"** —— 会被 exported 先挡掉，得出错误结论。
> 正确做法：观察 app 自投的 alarm 记录（`caller=com.android1IN42343.client ... uid=10308`），或改用 `exported=true` 的接收器。

### 7.2 `am broadcast BOOT_COMPLETED` 会被权限拒绝

```
java.lang.SecurityException: Permission Denial:
  not allowed to send broadcast android.intent.action.BOOT_COMPLETED
  from pid=4216, uid=2000
```

这是 adb 权限问题，**不是**冻结问题，两者不可混谈。

### 7.3 `/proc/self/cgroup` 自检不可用

进程冻结时无法执行代码；且冻结/解冻是 1s 级反复，采样极大概率落在解冻窗口，得出"没被冻"的假象。

- 检测冻结的**正确信号**：墙钟 vs `SystemClock.elapsedRealtime()` 的差值
  ```
  frozenGap = (wallNow - wallPrev) - (elapsedNow - elapsedPrev)
  ```
- 排查时用**外部**采样：`adb shell cat /proc/<pid>/cgroup | head -1`，5s 一次。

### 7.4 `dumpsys alarm` 的 `last -XmYs` 只证明"闹钟到点了"

它按 wakeup 记账，**不证明广播被投递**。判定投递必须看 `dumpsys activity broadcasts` 里的 `DELIVERED` / `SKIPPED` 与 `caller=` 字段。

### 7.5 `context.stopService()` 停不掉 `VpnService`

改完 `STOP_VPN_AFTER_SETUP=1` 后日志已打 `stopVpn ok`，但 `dumpsys connectivity | grep -c 'sessionId=SmartVpn'` 仍然是 `1`，TUN 一直挂着。

原因：`VpnService` 被 system_server 以 `BIND_VPN_SERVICE` 绑定着。

```
ServiceRecord{... com.vibelink.client.service.BlackholeVpnService}
  ConnectionRecord{... CR FGS android system 1000 ...}
```

有活跃绑定在，`stopService()` 不会走到 `onDestroy`。

**正确做法**：让服务自己关 TUN —— 发带 `ACTION_STOP` 的 Intent，服务在 `onStartCommand()` 里 `teardownTunnel()` + `stopSelf()`。

> 判据不要看日志、看 `dumpsys connectivity` 的 `sessionId=` 计数。日志打 `ok` 只代表 Intent 发出去了。

**这条修完之后又踩出一个反噬**：`startForegroundService()` 会先把服务创建起来再投递 `ACTION_STOP`，等于"为了关掉它先开一个前台服务"。setup 收尾那几秒有 5 个入口都会调 `stopVpn`，一次收尾就打了 4 条 `Background started FGS: ... act=...STOP_VPN`，`startForegroundCount` 也跟着涨——在 vivo/OPPO 那套"屡次停止"记账里是负分。

所以 `stop()` 前面必须加一道"实例是否真活着"的判据（`@Volatile` 静态引用，`onCreate` 赋值、`onDestroy` 清空）：没有实例就没有 TUN 可关，直接返回。同时把返回值改成"是否真的发了停止指令"，让 `stopVpn` 的日志能区分 `sent` 与 `noop: vpn not running`——否则日志永远是 `ok`，等于没打。

### 7.6 `buildConfigField` 不会把 `android-env.properties` 当作输入

改了 properties 里的值、构建、安装、复测，行为完全没变。两件事叠在一起：

1. **显式值压过默认值**：仓库根部 `android-env.properties` 写着 `STOP_VPN_AFTER_SETUP=0`，`build.gradle.kts` 里改默认值没用。
2. **Gradle 不认识这个文件**：`GenerateBuildConfig` 的输入里没有它，文件改了任务仍判 UP-TO-DATE，沿用上一次生成的常量。

**唯一可信的检查是直接看产物**：

```bash
grep STOP_VPN_AFTER_SETUP app/build/generated/source/buildConfig/release/com/vibelink/client/BuildConfig.java
#   public static final boolean STOP_VPN_AFTER_SETUP = false;   ← 与源码不符
```

已给 `GenerateBuildConfig` 显式声明 `inputs.files(androidEnvPropFiles)`。凡是从外部 properties 注入的 `buildConfigField`，都要走这一步；否则会得到"代码改了、开关也改了，但装机行为不变"的静默失败。

### 7.7 uid 会随重装漂移

同一条命令在不同轮次拿到 `10308` / `10310`，会让人误以为设备上跑了两份。实际是覆盖安装后 uid 重新分配。

- 别在脚本里硬编码 uid，用 `adb shell dumpsys package <pkg> | grep userId=` 或 `cmd package list packages -U` 现取。
- `dumpsys power` / logcat 里的历史 uid 只对应当时的安装，跨轮次不可比。
- 重装还会**清掉无障碍绑定与 `SetupPrefs`（DPS+CE 双写）**，`setupCompleted` 会被回写成 `false`，必须先重新授权再测。

### 7.8 「后台点唤醒无反应」先分清是客户端还是服务端

同一套代码在两台机器上部署状态可以完全不同，而这个差异**从设备日志里看不出来**——设备只是轮询到一个 404/401，然后什么都不做。

`APP_ENV` 决定设备打哪个后端（`android-env.properties`），探针要按同样的地址打：

```bash
# 设备轮询接口是公开路由，不加 token 就能判断"路由是否存在"
curl -s -o /dev/null -w "%{http_code}\n" "$BASE/api/device/zombie-wake"
#   200 → 已部署
#   401 → 未部署（被 isProtectedRequest 兜住，和拼错的路径返回一样）

# 对照组：一个根本不存在的路径，正常也返回 401
curl -s -o /dev/null -w "%{http_code}\n" "$BASE/api/device/__probe__"
```

两个都 401 就说明该路由不存在；一个 200 一个 401 才说明已部署。

本轮实测（2026-11-06，两台均已部署）：

| 地址 | 解析到 | `/api/device/zombie-wake` | 到 Google 的出站 |
|---|---|---|---|
| `http://8.155.130.49:18083`（`DEV_API_BASE`） | `8.155.130.49` | 200 | **不通**（`http=000`） |
| `https://app.wjbk1688.online`（`PROD_API_BASE`） | `47.84.116.171` | 200 | **通**（`http=404`） |

**两台是不同的机器，别假设改了哪台另一台就跟着变。** 而且「路由已部署」和「推送发得出去」是两件事——前者 200 不代表后者，必须看 `nudgedFcm` / `fcmReason`。

### 7.8.1 先用两条 curl 分清「代码」还是「网络」

服务端发不出 FCM 时，先测出口，别急着翻代码：

```bash
curl -m 10 -o /dev/null -w "oauth %{http_code} %{time_total}\n" https://oauth2.googleapis.com/token
curl -m 10 -o /dev/null -w "fcm   %{http_code} %{time_total}\n" https://fcm.googleapis.com/
```

- `404` → TLS 与出站都正常，问题在凭据/权限/代码
- `000` 且耗时≈超时阈值 → **出口被墙**，改代码没用，换机或加代理

再补一条对照组确认不是断网：

```bash
curl -m 8 -o /dev/null -w "baidu %{http_code}\n" https://www.baidu.com
```

`baidu=200` 而 Google 全 `000` = 选择性封锁，不是网络故障。

> 别把 DNS 当嫌疑人。本轮 `8.8.8.8` 返回的是真实 IP（`74.125.20.95` / `216.239.36.55`），污染不成立；扫了 17 个 Google 的 443 IP 全部不通，只有 GCS 前端能握手（返回 404/400，根本不是 API 端点）。判定在 IP 层，不在域名层。

### 7.9 「SSH 连不上」先换个源再下结论

生产机 `47.84.116.171` 只对白名单 IP 开放 SSH，表现很容易误判：

```
从本机：  TCP 能连上，但读到空 banner → kex_exchange_identification: Connection closed
从白名单：SSH-2.0-OpenSSH_8.9p1 Ubuntu-3ubuntu0.18
```

**「TCP 通 + banner 空」不是服务挂了，是安全组/fail2ban 在放行 SYN 之后直接掐断。** 遇到这种先换一台可信机器（比如另一台同机房服务器）验证，再决定是不是要加白名单；否则会一直怀疑自己的客户端或密钥。

跳板写法（本机 → 8.155.130.49 → 47.84.116.171）：

```bash
ssh -o ProxyCommand="ssh <跳板> -W %h:%p" root@47.84.116.171
```

### 7.9 管理端登录失败两次就锁号

`FAIL_LIMIT=2`，超限后返回 `login_blacklisted`，而且**按用户名和 IP 双向匹配**（`isLoginBlacklisted` 的 SQL 是 `username = ? OR ip = ?`）。所以同一个出口 IP 上试错，会把该 IP 上所有账号一起拖下水。

- 不要靠猜口令来验证部署。
- `invalid_credentials` 说明用的是"口令不对"这条分支，`login_blacklisted` 说明已经锁了；两者的响应能区分当前状态。
- 线上排查优先用公开路由（如 `/api/device/*`）和 `/health`，不碰登录。

## 八、下一步

本轮完成五件事：常驻 wakelock 的 A/B 证伪（§零、§二）、FCM 通道的实机验证（§4.7）、Firebase 工程接入（§4.8）、`patchScreenOffTimeout` 永久污染 bug 的修复与 6/6 实机验证（§4.7(b)）、以及**黑洞 VPN 常驻这个真根因的定位与端到端修复**（§4.9）。

### 已可宣告的结论

- **wakelock 是死路**。`handleCheckWakelock` 10s 清锁 + Hiber 不看 wakelock，两条独立机制，竞品那套在本机同样无效。
- **`c2dm` 广播是本机唯一获准穿透冻结的普通 app 通道**，且已验证能解冻、能亮屏、亮屏后不被重新冻结。
- **FCM 接入不会打断打包**。json 缺失/包名不匹配都自动降级为 `FCM_ENABLED=false`，构建照常成功；马甲换包名不再需要改构建脚本。
- **FCM 一直没坏，坏的是自家 VPN**。`BlackholeVpnService` 常驻并把 GMS 关进只读 TUN，导致 `SERVICE_NOT_AVAILABLE`。改为 setup 完成后停止（`STOP_VPN_AFTER_SETUP=1`）即恢复，端到端已实测通过。

### 服务端：根因是出口墙，已换机解决

**测试机 `8.155.130.49` 的 FCM 永远发不出去，原因不在代码、不在凭据，在出口网络。**

排障时逐层否掉了三个猜测：

| 猜测 | 实测 | 结论 |
|---|---|---|
| 代码没部署 | `remote_control_baxi/api` 里有 `fcm-wake.service.ts`、有 `pushZombieWake` | 否 |
| 凭据没带上 | `firebase-adminsdk.json` 在，`project_id = minishot-c9249`，与设备端一致 | 否 |
| 路径解析不到 | 进程以 `www` 启动、cwd 就是 `api/`，相对路径能解析 | 否 |
| **到 Google 的出站** | `oauth2` / `fcm` / `www.google.com` 全部 `http=000`，10s 超时 | **是** |

不是 DNS 污染——`8.8.8.8` 返回的是真实 IP（`74.125.20.95` / `216.239.36.55`）。是**IP 层封锁**：扫了 17 个 Google 的 443 IP 全不通，只有 `storage.googleapis.com` 那几个 GCS 前端能握手（返回 404/400，根本不是 API 端点）。同机 `baidu`、`github`、`cloudflare`、`npm` 都是 200，说明是选择性封锁，不是断网。

这台机器上 `POST /api/devices/zombie-wake` 的真实返回：

```json
{"needWake":true,...,"nudgedOnline":1,"nudgedFcm":false,"fcmReason":"fcm_send_timeout_8000ms"}
```

接口耗时正好 8.008s——**8s 超时生效了**，没有把请求拖成 nginx 504。这反过来证明 `nudgedFcm` / `fcmReason` 这套自检字段是对的：静默降级被如实报了出来，只是那一刻没人看。

**生产机 `47.84.116.171` 完全正常**：`oauth2` / `fcm` 都是 `http=404`（TLS 通，30ms），`google.com` 200。同一份代码同一份凭据，两台机器结果相反——问题从头到尾都是网络。

> 一个容易误判的细节：生产机只对白名单 IP 开放 SSH。从本机连是「TCP 通但 banner 为空」（fail2ban/安全组的表现），从 `8.155.130.49` 连则正常返回 `SSH-2.0-OpenSSH_8.9p1`。排障时若不换源尝试，很容易误判成「SSH 服务挂了」。

条件：设备 `frozen` + `mWakefulness=Asleep`，从生产机 `POST /api/devices/zombie-wake`。

### 一个真实的安装期缺口（已修）

排障中发现：**14:19:56 全新安装后，FCM 订阅一直没成功，直到 14:31:32 手动重启进程才订阅上。**这中间本地探针与服务端推送都唤不醒设备，只有 HTTP 轮询在兜（而轮询恰恰是冻结时唯一无效的那条）。

原因：`subscribe()` 的重试链总长只有 `15+30+60+120 = 225s`。安装期进程先于 setup 完成启动，首轮必然被黑洞 VPN 挡成 `SERVICE_NOT_AVAILABLE`；一旦这 225s 耗尽，而用户之后没再走过 setup 收尾，`subscribeAfterSetup()` 就不会再被调用——设备从此收不到唤醒，**只有重启进程才恢复**。

修复：新增 `ensureSubscribed()`（已订阅时只做一次原子读、不打日志），挂在僵尸唤醒轮询里。轮询是唯一常驻的定时入口，天然是兜底点；30s 一次的轮询顺带把订阅补回来，不会刷屏。
