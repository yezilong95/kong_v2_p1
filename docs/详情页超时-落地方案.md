# 详情页超时 / 失败 — 分层落地方案

> 目标：消除「列表页显示在线、无障碍已允许、进入详情页经常超时或失败」这一现象。
> 口径：**只写策略与验收标准**，不含代码。每层落地独立可发布、独立可回滚（`git revert` 对应提交即可）。
> 前置结论见仓库同目录 / 旁路分析：`详情页超时-排查结论.md`（如有）或对话历史中的「Minishort 对照」。

---

## 零、问题模型回顾（一句话）

- **在线语义失真**：`ConnectionManager.OFFLINE_GRACE_MS = 12_000` 把宽限期内设备算在线，但 `sendCommand` 严格要求 socket OPEN。
- **详情页高频拉模型**：`ScreenViewer` 每 500ms 发一条 `get_ui_tree`，`waitMs: 12000`。
- **设备端无并发控制**：`ConnectionService.onCommand` 所有分支 `serviceScope.launch`（`Dispatchers.IO`，64 线程），无串行、无去重、无互斥。
- **UI 树采集过重**：`maxNodes 2000`、`fullMode` 全叶子、`scoreUiWindowRoot` 里再做一次 `hasViewIdInTree` 全树深搜，单轮 2 万+ IPC。
- **跨线程访问无障碍 API**：`rootInActiveWindow` / `windows` / `getChild` 等在 IO 线程调用，并发会把 Binder 挤到超时。
- **报文与心跳同通道**：500KB UI 树和控制命令、ping 走同一条 WS 写队列，无水位判断。
- **迟到结果被静默丢弃**：ephemeral 命令超时后，设备真的返回也无处认领，且不广播给 admin。

修复按改动面从小到大划分 L1 / L2 / L3。**L1 不改协议、不改前端轮询周期**，先止血；L2 调结构；L3 换协议语义。

## 一、L1 · 止血层（当周可发布）

目标：**消除「正在跑的 dump 被下一轮并发打断」这一主因**，让单台设备在同一时刻只有一条 UI 树采集在跑；超时不再是"真超时"，而是"主动截断并返回部分结果"。

### L1-1 设备端：重命令单实例互斥

**范围**：`Android/app/src/main/java/com/vibelink/client/service/ConnectionService.kt` 的 `onCommand`。

**策略**：
- 识别"重命令"白名单：`get_ui_tree`、`get_screen`、`capture_screenshot`、`dump_keyguard_tree`。
- 对白名单命令，按 `cmd` 维度维护在途标记（AtomicBoolean 或 Mutex.tryLock）。
- 若已在途：**立即回执** `ok=false, error="superseded"`，**不要排队**，不要等前一轮。
- 非白名单命令行为不变。
- `switch_server`、`update_apk`、`ensure_screen_channel` 不进互斥。

**为什么不排队**：UI 树是"快照型"数据，迟到的结果没有价值；排队只会把延迟摊到后续请求上，正反馈更严重。

**验收**：
- adb logcat 中同一秒内 `get_ui_tree` 的进入日志最多一条。
- 前端 `UI 树失败：superseded` 偶尔出现是预期的，比 `wait_timeout` 更快返回（<100ms）。

### L1-2 设备端：无障碍 API 全部回到主线程

**范围**：`RemoteAccessibilityService.dumpUiTree` 及其调用链（`collectUiTreeRoots` / `appendUiTreeNodes` / `scoreUiWindowRoot` / `hasViewIdInTree`）。

**策略**：
- `AccessibilityControlBridge.dumpUiTree` 内部用 `withContext(Dispatchers.Main)` 把整段遍历包起来。
- 所有 `rootInActiveWindow`、`windows`、`getChild`、`getBoundsInScreen`、`isVisibleToUser` 调用必须在主线程。
- 结果 JSON 的拼装（`JSONObject.put`）可以留在当前线程，Binder 结果读完就 release，不要带着 node 跨线程。

**为什么必须**：`AccessibilityInteractionClient` 对同一服务的并发 Binder 请求有连接级互斥与 5s 交互超时。IO 线程并发访问会相互阻塞，表现为"树突然变空"、"节点缺失"、"单轮耗时从 800ms 跳到 5s+"。

**验收**：
- 开启 StrictMode `detectCustomSlowCalls`，不应再出现非主线程访问无障碍 API 的告警。
- `no_root` 返回占比下降（可通过 admin 侧统计 ephemeral 错误码采样）。

### L1-3 设备端：dump 超时保护

**范围**：`RemoteAccessibilityService.dumpUiTree`。

**策略**：
- 整个 `dumpUiTree` 外包 `withTimeoutOrNull(3_000)`。
- 超时后返回 `truncated=true` + 已采集的部分节点（不是报错），字段里带 `elapsedMs`、`timedOut=true`。
- 遍历内部按时间轮询退出：每处理 100 个节点检查一次 `System.currentTimeMillis() - startMs > 2500`，到点就停。

**为什么 3 秒**：前端 `waitMs=12000`、服务端 pending 也是 12s，设备端 3s 截断能保证"控制端永远在 4s 内拿到回执"，剩余 9s 留给网络和服务端。

**验收**：
- 低端机（4GB RAM、Android 10）长按刷新也不会出现 `wait_timeout`，最多是 `truncated=true` 的部分树。
- 单轮 `elapsedMs` P95 < 2500ms。

### L1-4 设备端：发送前轻量水位判断

**范围**：`DeviceWebSocketClient.sendRawMessage`，或在 `sendCommandResult` 层加包装。

**策略**：
- 发送前读取 `webSocket.queueSize()`（OkHttp 提供）。
- 对"可丢快照型"消息（`get_ui_tree` 的 result、`get_screen` 的 result、`capture_screenshot` 的 result）设阈值 **128KB**：超阈值**直接丢弃本次返回**并日志 `drop_stale_frame cmd=... queue=...`。前端会在下一轮重试。
- 对"不可丢"消息（命令回执除上述三种之外、心跳、键盘事件、信令）**永不丢**。
- 丢弃时仍要清理 L1-1 的在途标记，否则下一轮也进不来。

**为什么不照搬 Minishort 的 196608**：你们的报文更大，阈值更保守一些。

**验收**：
- 弱网限速到 1Mbps 上行，设备端不再出现"ping 被挤到 60s 才发"的现象（logcat `heartbeat` 间隔稳定 30s）。
- 丢帧率上升但详情页"卡住不刷新"的时长明显下降。

### L1-5 服务端：迟到结果也要广播

**范围**：`Manage/api/src/services/command.service.ts` 的 `applyCommandResult`。

**策略**：
- ephemeral 命令即便 `pendingWaits` 已超时清理掉，也要 `broadcastToAdmins({ type: "command_result", ... })`。
- 对应前端 `useAdminWebSocket.ts` 当前过滤 `get_ui_tree` 等 ephemeral 的逻辑放开，让 `ScreenViewer` 能通过 WS 直接收到最新树（不必再等下一次 HTTP 返回）。
- 前端在 `sendCommand` 已超时的情况下，若 WS 收到同 `commandId` 的结果，仍可更新快照，但**不再反显 `wait_timeout`** 为错误（改为"已超时但稍后恢复"）。

**为什么要做**：这是 L1 唯一动服务端+前端的改动。设备算完了的那份 500KB 不该被扔掉，否则 L1-3 的截断也白截。

**验收**：
- 人为在设备端 `sleep(5s)` 再返回，前端应看到先 `wait_timeout`、约 5s 后快照刷新，而不是永远停留在错误态。

### L1 整体验收

| 指标 | 现状基线 | L1 目标 |
|---|---|---|
| 详情页打开 10s 后 `wait_timeout` 占比 | 需测 | < 5% |
| 单轮 `get_ui_tree` P95 耗时 | 需测 | < 2500ms |
| 设备端同一时刻并发 dump 数 | 1–3 | ≤ 1 |
| `heartbeat` 实际间隔 P95 | 需测（弱网飘到 60s+） | < 35s |

## 二、L2 · 结构层（两周内发布）

目标：**消除轮询的浪费**，让多个 admin 共享同一份在途结果；前端退避把 500ms 这个"固定快周期"挪掉。

### L2-1 服务端：Single-flight 合并

**范围**：`Manage/api/src/services/command.service.ts`。

**策略**：
- 新增 `inflightEphemeral: Map<string, Promise<...>>`，key = `${deviceId}:${cmd}`（只针对 ephemeral 快照类命令）。
- `sendCommand` 进入时若命中 inflight：**不再**插入新的 pendingWaits，直接 `await` 已有 Promise 的结果。
- `applyCommandResult` 回填后清理 inflight；超时也清理。
- 对 `get_ui_tree`、`get_screen`、`capture_screenshot` 启用；其他命令绕过。

**为什么做**：同一台设备 3 个 admin 同时开详情页，设备端只采集 1 次；并且 L1-1 的"superseded"场景在服务端就被吸收掉，不会打到设备。

**验收**：
- 3 个 admin 同时打开同一设备详情页，设备 logcat 中 `get_ui_tree` QPS 不翻倍。
- 服务端新增指标 `ephemeral_singleflight_hit_total`，命中率 > 50%（多人盯同一台时）。

### L2-2 前端：轮询退避 + 变化去抖

**范围**：`Manage/web/src/components/ScreenViewer.tsx` 的 `pollUiTree`。

**策略**：
- `UI_TREE_POLL_MS` 500 → **1000 起**；连续失败按 1s → 2s → 4s 指数退避，上限 4s；成功一次复位到 1s。
- 快照签名（`packageName + nodeCount + 前 10 个节点的 viewId 拼接哈希`）和上一次相同时**不触发 React 重绘**，仅更新 `lastSuccessAt`。
- `superseded` 不计入失败计数（它代表设备仍健康，只是前一轮没完）。
- `wait_timeout` 计入失败计数。

**为什么**：500ms 是直觉数字，实际用户肉眼的反馈周期 >200ms 就感知不到了。1s + 变化推送 完全够用，还能让快照稳定不抖。

**验收**：
- 空闲页面（设备 UI 不动），前端 `get_ui_tree` 请求频率从 2 Hz 降到 1 Hz；网络 panel 观察数据体量下降 ≥ 50%。
- 设备端带宽占用（logcat `queueSize`）在同样场景下下降到 L1 之前的 40% 以内。

### L2-3 "在线"语义拆分

**范围**：`Manage/web/src/pages/RemoteControlPage.tsx`、`DeviceListPage.tsx`，及 API `/api/device` 返回。

**策略**：
- 后端 `Device` 增加三档健康度字段：`controlOk`（控制 WS OPEN）、`a11yRtt`（最近一次 ephemeral 命令往返毫秒数，滑动窗 60s）、`adbOk`（ADB 通道是否可用）。
- 详情页顶部用三个独立徽标展示，而不是单一绿色圆点。
- 列表页仍可用单一在线色，但 tooltip 要显示三档明细。

**为什么**：当前"显示在线但详情页失败"的落差就是单一绿色掩盖了另两档。给用户肉眼可见的分层，排障时能一眼定位是哪层坏了。

**验收**：
- 人为关闭无障碍，列表页仍显示在线（控制通道通），但详情页 `a11yRtt` 徽标变红。
- 人为切飞行模式，三档在 15s 内全部变红。

### L2-4 设备端：删除无谓的全树扫描

**范围**：`RemoteAccessibilityService.scoreUiWindowRoot` 中的 `hasViewIdInTree(root, PIN_CONTAINER_VIEW_ID)`。

**策略**：
- 只在"当前在锁屏包名下"才执行 PIN 容器探测，其他场景跳过（整个 dump 省一次全树遍历）。
- 判断条件可以用 `KeyguardManager.isKeyguardLocked` 或包名前缀 `com.android.systemui` / OEM 锁屏包白名单。
- 其他 `score += ...` 的加分项保留。

**为什么**：这个探测每次 dump 都对每个 root 深搜一次，在非锁屏场景完全是浪费，占单轮耗时的 10–30%。

**验收**：
- 非锁屏场景 `dumpUiTree` 单轮耗时下降 ≥ 15%。
- 锁屏场景 PIN 面板识别功能不受影响（回归测试：进锁屏仍能定位 PIN 容器）。

### L2 整体验收

| 指标 | L1 后 | L2 目标 |
|---|---|---|
| 单轮 `get_ui_tree` P95 | < 2500ms | < 1500ms |
| 多 admin 共盯同设备时设备侧 QPS | 线性叠加 | 不变 |
| 前端 `wait_timeout` 占比 | < 5% | < 1% |
| 列表→详情页首帧可见 UI 树 | 需测 | < 2s |

## 三、L3 · 协议层（当月内发布）

目标：**从"控制端拉"换成"设备端推"**，彻底消掉固定周期；接近 Minishort 的模式，但保留你们 WebRTC + 分通道的优势。

### L3-1 新增 UI 树订阅通道

**范围**：新增 WS 子通道或复用 `DeviceScreenWebSocketClient`。

**策略**：
- 新命令 `subscribe_ui_tree` / `unsubscribe_ui_tree`，前端进入详情页时 subscribe，离开时 unsubscribe。
- 设备端维护订阅状态，不再响应 `get_ui_tree` 的周期性拉取（保留该命令用于一次性调试）。
- 推送通过画面通道（`DeviceScreenWebSocketClient`）或新独立通道走；**不占控制通道写队列**。
- 消息体 `{ type: "ui_tree_push", deviceId, seq, snapshot }`，`seq` 单调递增，前端只接受更大 seq。

**为什么分通道**：UI 树和画面同为"快照流"，共享一个写队列可以用同一套水位策略；控制通道只走命令和心跳，永远畅通。

**验收**：
- 关闭前端轮询后，详情页仍能持续看到 UI 树刷新。
- 控制通道 QPS 回落到只有命令 + 心跳。

### L3-2 设备端：事件驱动推送

**范围**：`RemoteAccessibilityService.onAccessibilityEvent` + 独立调度器。

**策略**：
- 监听 `TYPE_WINDOW_STATE_CHANGED`、`TYPE_WINDOW_CONTENT_CHANGED`、`TYPE_VIEW_SCROLLED`。
- 去抖 200ms：事件触发后 200ms 内合并多次为一次 dump。
- 节流下限 800ms：两次推送最短间隔 800ms，保证极端场景（滚动列表）不打爆。
- 空闲心跳 5s：即使没事件也每 5s 推一次（给 admin 新连上时用），内容若与上次完全相同可只推 `seq` 心跳。
- 推送前复用 L1-4 水位判断，超水位丢本次。

**为什么**：Android 视图变化本身是事件驱动，监听成本极低；比 1Hz 轮询更贴合实际变化频率。

**验收**：
- 页面无操作 30s，推送数应 ≤ 6（空闲心跳）。
- 点一次按钮，前端应在 400ms 内收到新快照。

### L3-3 新订阅者快速补帧

**范围**：服务端 `admin-screen.ws.ts` 或新 handler。

**策略**：
- 服务端对每台在线设备缓存"最近一份 UI 树快照"（内存即可，不落库）。
- 新 admin subscribe 瞬间先回放缓存快照，然后开始接收 push，避免首屏空白。
- 缓存设 TTL 10s；超时后请求设备端"强制全量推送一次"。

**为什么**：切换到推模式后，新连上的 admin 本来要等下一次事件才有数据；补帧能保持 L2 的「首帧 <2s」体验。

**验收**：
- 刷新详情页，UI 树在 500ms 内可见（本地缓存命中）。
- 设备 10s 内无变化，刷新也应看到数据（设备回退到强制全量）。

### L3-4 可选：WebRTC DataChannel 承载

**范围**：复用现有 WebRTC 连接。

**策略**：
- 若 WebRTC 已连通，优先用 DataChannel 送 UI 树快照；WS 作为降级。
- DataChannel 本身有拥塞控制，不需要手工水位。

**为什么可选**：改动最大，收益在高丢包网络下最明显；可以作为 L3 之后的增量项，不阻塞 L3 主体。

**验收**：
- 高丢包测试（loss 5%）下 UI 树刷新率不下降超过 30%。
- DataChannel 断开自动降级到 WS，用户无感。

### L3 整体验收

| 指标 | L2 后 | L3 目标 |
|---|---|---|
| 页面空闲时后台 UI 树 QPS | 1 Hz | ≤ 0.2 Hz（空闲心跳） |
| 页面操作后快照响应延迟 P95 | ≤ 1500ms | < 500ms |
| 详情页"进入即可用" | < 2s | < 500ms |
| 控制通道心跳抖动 | 稳定 | 稳定且带宽 < 1KB/s |

## 五、发布节奏与风险控制

- **L1 独立发布**：任一子项都可单独上灰度，互相无依赖。优先出 L1-1、L1-2、L1-3，一周内看指标。
- **L1-5 前后端配套发布**：服务端先上（向前兼容，旧前端接收不到 push 也没问题），前端再上。
- **L2 依赖 L1 稳定**：L2-1 要求设备端已经有互斥（L1-1），否则 single-flight 聚合的请求打到设备会直接 `superseded`。
- **L3 单独规划 sprint**：协议改动需要前后端 + 设备端三端联动，建议同一版本号卡点发布，灰度时先放 5% 设备。
- **回滚**：每层每个子项独立 PR / 独立提交，出问题 `git revert` 单条即可；无数据库迁移，无前向不兼容配置。

## 六、衡量指标（建议统一埋点）

建议在 `Manage/api` 侧新增内存计数器（Prometheus 或日志打点都行），至少覆盖：

- `ephemeral_cmd_total{cmd, result}` — result ∈ {ok, superseded, wait_timeout, dropped, error}
- `ephemeral_cmd_duration_ms{cmd}` — 直方图
- `singleflight_hit_total{cmd}` — L2-1 命中次数
- `device_health{deviceId, dim}` — dim ∈ {control, a11y, adb}

有了这些指标才能客观判断 L1 → L2 → L3 的收益；没有的话容易陷入"感觉好像好点了"的玄学。
