## 零、结论摘要

**一句话**：1688 的无障碍是**自动开启**的，管理端不参与。它靠 ADB 换来的一个系统级落点完成闭环：

| 落点 | 手段 | 何时生效 |
|---|---|---|
| `WRITE_SECURE_SETTINGS` | `pm grant`（经本地 ADB shell） | 配对成功后，`Z1()` 内，紧接睡 600ms |
| ADB shell 本身 | `settings put secure`（shell uid 天然有该权限） | 代码里存在，但**条件写反，实际不生效**（见 §三 L1） |

四条硬结论：

1. **首次安装必须人工开一次无障碍**。自动配对（`AUTO_PAIR_START`）本身要靠无障碍点 UI，服务没起来就直接 abort（`o0.java:2360` 明确写了 `accessibility not ready`）。这是整个方案的起点，绕不过去。
2. **配对成功之后无需任何人工操作**。`Z1()` 里先 `pm grant`，再由 `l2()` 起 5 秒监控线程，第一轮就把无障碍写回去。按代码推算：`pm grant` 后睡 600ms，监控线程首轮再睡 5s 才判定，故首次恢复在 **5.6 秒之后**（此为推算值，非实测）。
3. **真正干活的只有一条路径**：`WRITE_SECURE_SETTINGS` + 5 秒轮询。`t2.l0()` 那条 shell 直写在 DO 分支里，但进入条件是「无障碍已经在设置里」，而 `l0()` 自身又会早退，所以它**在任何状态下都不产生实际写入**。这个 bug 对整个方案的性质判断很关键，详见 §三。
4. **管理端只能开关自愈，不能代替开启**。命令表里无障碍相关共四条：`access_restore_on/off/now` 与 `access_disable`；前三条的默认态已经是 `on`（`o0.java:106`，`M = true`）。

**这套方案不能整段照搬到我方**，原因见 §六：它设计上的三级恢复里，**L1（ADB shell 直写）因条件写反是死代码，L2（进程内写）需要 `WRITE_SECURE_SETTINGS` 而当前没有，L3（UI 引导）在竞品里只是降级兜底**。可借鉴的是「四态判定 + toggle 重绑 + 前台引导」，不是「静默写设置」。

### 本轮最有价值的两条，来自真机实测（不是读代码）

1. **③（设置里有、服务没绑）的修法是 toggle**：把本服务从 `enabled_accessibility_services` 里摘掉、再挂回去，就能恢复绑定；**重写同值完全无效**。摘掉后不 sleep 也行（实测 0s 成功），也不需要同时写 `accessibility_enabled=1`。toggle 还会顺带把已死的进程拉起来。详见 §7.5。
2. **`accessibility_enabled=0` 不等于无障碍不可用**：在服务已绑定的前提下把这个值改成 0，服务照样活着、照样绑定。所以「开关值」不能当 ① 的首要判据——我方现有 `getServiceStatus()` 会在这里误报。详见 §7.6。

这两条都直接改变我方要写的代码，优先级高于任何竞品机制细节。

## 一、四个状态与竞品的判定方式

竞品内部只有**一个**判定函数，就是 `ut0.b()`（`ut0.java:27`）：

```

按 ':' 拆开，逐个 ComponentName.unflattenFromString
与本服务 ComponentName 做 equals 比较
```

它**只看设置字符串，不看服务实例**。配合 `tbzdqklwqv.j`（静态字段，持有 `AccessibilityService` 实例引用，`tbzdqklwqv.java:57`）才凑出两维信息：

| 态 | 设置字符串含本服务 | `tbzdqklwqv.j != null` | 竞品处理 | 代码位置 |
|---|---|---|---|---|
| ① 系统开关关 | ✗ | — | `W1()` 补写字符串 + `accessibility_enabled=1` | `o0.java:1639` |
| ② 系统开关开、服务未绑定 | ✗ | ✗ | 同 ①，合并处理 | 同上 |
| ③ 设置里有、实例未连 | ✓ | ✗ | `h0()` → `X0()` **toggle 重绑** | `o0.java:1269` → `2989` → `1742` |
| ④ 正常 | ✓ | ✓ | 不动 | — |

**竞品不区分 ①②**（判据一样），但**必须区分 ②③**——因为两者的修法完全不同：

- ② 修法：把字符串写进去就行，系统会自己 bind。
- ③ 修法：把字符串**先删再写**，制造一次「配置变更」，逼系统重新 bind。纯重写（值没变）不触发任何回调，等于什么都没做。**这一点已在 CPH2783 实测确认**（§7.5）。

**但竞品的二维模型漏了一件事**：它把 ① 定义为「`accessibility_enabled` 关」，只靠 `ut0.b()` 的结果反推，**从未直接读 `accessibility_enabled`**。而实测（§7.6）表明这个值关了服务照样绑定。所以竞品的 ① 实际上只会在「列表里没有本服务」时才触发——它自己的 ① 和 ② 在代码里根本是同一条路径。这不是设计取舍，是判据不足。

我方 `AccessibilityHelper.getServiceStatus()` 分 `disabled` / `not_bound` / `enabled` 三态，信息量比竞品多，但引入了一个新问题：`!isAccessibilityManagerEnabled()` 优先级最高，会在 §7.6 那种「开关关了但服务活着」的场景误报 `disabled`。竞品反而不会误报（它压根不读那个值）。**两边的错法不同，需要合成一个正确的四态**（§7.1 给了建议顺序）。

### 2.2 配对环节的两个技术点

**配对端口 ≠ 连接端口。** 配对走 `_adb-tls-pairing._tcp`，连接走 `_adb-tls-connect._tcp`（常量在 `o0.java:67-68`）。配对完成后端口会重分配，代码里 `X()` 的尝试顺序是：上次保存的端口 → mDNS `_adb-tls-connect` → UI 读到的端口 → `5555` 明文兜底（`POST_PAIR_TRY_5555_RSA`）。

**配对码的信任是持久的。** SPAKE2 成功后把证书存两份：

- `SharedPreferences("adb_conn").putString("last_pairing_cert_b64", ...)` —— 供自己重连用；
- `t2.q0("sh -c '... >> /data/misc/adb/adb_keys ...'")`（`o0.java:2174`）—— 写进系统 adb 授权文件，**重启后 adbd 仍然信任它**。

第二条是长期存活的关键：一次配对，永久有效。

### 2.3 「自动」到什么程度

| 环节 | 是否需要人 |
|---|---|
| 开启无障碍（首次） | **需要**，否则 `AUTO_PAIR_START` 直接 abort |
| 开开发者选项 / 无线调试 | 不需要，无障碍点 UI |
| 输配对码 | 不需要，无障碍从屏幕读 |
| `pm grant` | 不需要 |
| 写无障碍设置（配对后的首次） | 不需要，但**前提是 `pm grant` 成功**；失败则整条链失效 |
| 掉线后恢复 | 不需要（见 §三），同样以 `pm grant` 成功为前提 |

`AUTO_PAIR_START` 里那句 abort 是硬约束：

## 三、三级恢复体系

竞品**设计上**有三条可选的恢复路径，但按代码看只有一条真正生效。

### L1 · ADB shell 直写（设计上最强，实现有 bug，实际不生效）

`t2.l0()`（`t2.java:2869`）：

```

  → 已含本包名：直接 return true（不写）
  → 否则拼上本服务，然后
settings put secure enabled_accessibility_services <值>
settings put secure accessibility_enabled 1
```

这条走 `q0()` → adbd，**shell uid 天然持有 `WRITE_SECURE_SETTINGS`**，设计意图是连 `pm grant` 是否成功都不依赖。

但调用点只有一个，`o0.java:2107`：

```java

    t2.l0(context);

    "runPostConnectTasks: accessibility OFF, auto-restore disabled by operator";

```

这里有两个互相抵消的错误，使它成为死代码：

1. **进入条件反了**。`ut0.b()` 为真表示「无障碍已在设置里」。而 `l0()` 内部第一件事就是 `if (strQ0.contains(packageName)) return true` —— 已在设置里就直接返回、不写。所以进得来的时候 `l0()` 必然早退，进不来的时候（无障碍真的关了）分支根本不会进。**任何状态下都不产生写入。**
2. **`else if` 的日志也在撒谎**。真进了 `else` 分支说明无障碍确实关了，它却打印「auto-restore disabled by operator」，把「已被关掉」误报成「运维主动关闭了自愈」。

正确的写法应当是 `if (!ut0.b(...) && M)`。这说明该分支很可能从未在真实设备上验证过——如果验证过，`ACCESS_RESTORED|local_adb` 这条日志要么永不出现，要么出现时无障碍本来就是好的。

外层还包着 `if (kp0.i(context) || g0)`（`o0.java:2097`，`kp0.i()` = `isDeviceOwnerApp`，`kp0.java:108`），`g0` 在 `Z1()` 末尾置 true（`o0.java:2189`），所以第二次起外层不再拦。但问题在内层，与外层无关。

顺带：`Z1()` 会尝试 `dpm set-device-owner`（`o0.java:4743`），成功则把自己变成 DO 并 `setUninstallBlocked`。

```java
    break;
```

后面两个 `try` 各自带 `break`，所以只要第一个 `try` 不抛异常，`c1()`（`p2.java:1532`，内部调 `o0.U()`）**根本不会执行**。`j0.Z(false,true)` 走的是 `Q1()`（`j0.java:1944`）——只是 `H7()` 摘掉覆盖层 + `D8()` 销毁 WebView，**并不关闭系统无障碍开关**。

也就是说：`access_disable` 在当前实现里**大概率只清自愈开关和覆盖层，不真正关闭无障碍**。`o0.U()`（`o0.java:1432`，那段对称的 remove + `accessibility_enabled=0`）是存在的，但从这条路径够不到。

`o0.U()` 本身的写法是对称的、可用的：

```
把本组件从 enabled_accessibility_services 里 remove（含 :: → : 与首尾冒号清理）
accessibility_enabled = 0
```

注意它要求 `r0()` 为真，所以无权限时同样什么都不做。

（我要说明：`case 45` 的 jadx 输出把 `break` 放进了 `try` 块，这在 Java 里是合法的、也符合字节码结构；但由于反编译器的 `try`/`catch` 重建不完全可靠，这条结论建议用一次真机 `access_disable` 命令实测确认——看 `dumpsys accessibility` 的 `Enabled services` 是否被清空。已验证的是代码结构，未验证的是这一条的业务效果。）

## 六、与我方 B 包的对照

### 6.1 能力矩阵

| | 1688 | 我方 B（`com.android1IN42343.client`） |
|---|---|---|
| `WRITE_SECURE_SETTINGS` | 有（ADB 授予） | **无**，清单只声明了 `WRITE_SETTINGS` |
| 设备端 ADB 自配对（SPAKE2） | 有（原生库 + UI 自动化） | **无**，只有 `AdbWirelessAutomator` 的「开无线调试」能力，配对要人工 |
| Device Owner | 会尝试 `dpm set-device-owner` | 无（CPH2783 实测 `no owners`） |
| 检测 ①②③ | 有（字符串 + 实例） | 有（`getServiceStatus()` + `isReady()`） |
| ③ 的修法 | toggle 重绑（1.5s 非必要，实测 0s 可行） | 无 |

### 6.2 关键差异：权限这一层我方是空的

1688 的恢复链，最终**只剩 L2 一条真正生效**（L1 因条件写反是死代码，§三已述）。而 L2 的前提是两件事同时成立：

1. ADB 通道存在（才能 `pm grant`）；
2. `pm grant` 成功（`WRITE_SECURE_SETTINGS` 到手，5 秒循环才会被启动）。

我方现状：

- 没有 SPAKE2 配对实现，`AdbWirelessAutomator` 只能开无线调试面板、抓取配对码，**没有完成 handshake 的代码**；
- 因此即便把配对码抓到，也连不上 adbd，`pm grant` 无从谈起。

所以对我方而言，1688 的 L1/L2 **当前都不可用**，只有 L3（UI 引导）是现实路径。**但 L3 在竞品里是给「`pm grant` 失败」兜底的降级手段**——一个本不该常态触发的分支。我方要把它当作主路径来设计，因此必须比竞品做得更细：竞品在无权限时连弹窗都不弹（`o0.java:1250` 只上报一行日志），我方则要主动引导。

这也解释了一个容易被误读的现象：**竞品在 ColorOS / Hiber 这类机型上无障碍掉了之后，很可能什么都不会发生**——L1 是死代码，L2 循环压根没起来，L3 只在 `uq.a && uq.b` 都成立且 `!r0()` 时才弹。这不是「设计得很克制」，而是「链路上断了两截」。`[待验证]` 需真机观察。

### 6.3 可以立刻借鉴的四点

1. **③ 必须 toggle，不能重写** —— **已在 CPH2783 实测确认**（§7.5）。重写同值无效，摘掉再挂回有效；1.5s 延迟非必要（0s 也成功）；也不需要同时写 `accessibility_enabled=1`。这条直接决定我方 ③ 的文案该写成「关闭再开启」而不是「重启应用」——实测表明进程重启（`am start` 拉起进程）并不会重新绑定服务。
2. **`accessibility_enabled=0` 不等于服务不可用** —— **已在 CPH2783 实测确认**（§7.6）。这条直接影响我方判定：单看该值会误报 ①。
3. **①② 可以合并处理，③ 必须单独**。竞品因为判据只有字符串，天然把 ①② 合并了；我方 `getServiceStatus()` 分得更细，但引导动作上 ①② 本来就应该一样（都是「去开启」），所以合并不会损失信息。
4. **「状态机」比「重试循环」更值得抄**。竞品有 4 个状态、3 条修法，但没把「状态」和「修法」对应清楚，导致 L1 的进入条件写反还能一直留在代码里。我方按 ①②③④ 严格一一映射，比照抄它的三段式更有价值。

### 6.4 不建议照搬的部分

| 做法 | 为什么不建议 |
|---|---|
| 常驻 5 秒无限轮询 | 在 Hiber 冻结机型上一行都跑不了（见《僵尸唤醒与竞品保活机制-分析报告》§零），且耗电 |
| `dpm set-device-owner` | 需恢复出厂后 provisioning 阶段设定，存量设备补不上；且即便成为 DO，`setSecureSetting` 白名单不含 `ENABLED_ACCESSIBILITY_SERVICES`（见 §6.5） |
| 后台弹 WebView 引导页 | ColorOS 上 `default_background_activity_starts_enabled=false`，我方也没有 SAW / FULL_SCREEN_INTENT |
| 写 `/data/misc/adb/adb_keys` | 需要 root 或自身已是 adbd 授权方，链条太深 |

### 6.5 关于 DO 与无障碍的一条纠正

竞品确实会尝试 `dpm set-device-owner`，也在 DO 分支里做了 `settings put secure`。但**这两件事不是因果关系**：`settings put secure` 走的是 shell，shell 有权限；DO 不在 `setSecureSetting` 的白名单里。官方文档明确的可用键只有 `DEFAULT_INPUT_METHOD`、`SKIP_FIRST_USE_HINTS`（PO/DO）与 `LOCATION_MODE`（DO），**不含 `ENABLED_ACCESSIBILITY_SERVICES`**。

所以「让 B 变成 device owner 就能静默开无障碍」这条路不存在。DO 在本方案里的价值只有：BAL 豁免、静默装/卸载、`setPermissionGrantState`。

## 七、验收标准

若后续决定走「ADB 授权」路线（即补齐 SPAKE2 配对），按以下标准验收；若只走「UI 引导」路线，只看 §7.3。

### 7.1 L1 检测准确

| 项 | 标准 | 方法 |
|---|---|---|
| ① 判定 | `accessibility_enabled=0` **且**列表不含本服务 → `disabled` | 见下方注 |
| ② 判定 | 列表不含本服务 → `not_bound` | `settings put secure enabled_accessibility_services 'null'` |
| ③ 判定 | 列表含本服务、`isReady()==false` → 需另立状态 | `am crash <pkg>`（实测有效，见 §7.4） |
| ④ 判定 | 以上皆非 | 正常态 |
| 误报 | ④ 态下不得出现任何引导 | 静置 24h 观察 |

**① 的判据必须修正（实测依据见 §7.6）**：`accessibility_enabled=0` 但列表含本服务时，服务**仍然处于绑定可用状态**。所以不能单看这一个值。现有 `AccessibilityHelper.getServiceStatus()` 的 `!isAccessibilityManagerEnabled() -> "disabled"` 这一条优先级过高，会把可用状态误报成 ①。建议的判定顺序：

```
1. 列表不含本服务                → ② not_bound（不管 accessibility_enabled）
2. 列表含 + isReady() == true    → ④ enabled（不管 accessibility_enabled）
3. 列表含 + isReady() == false   → ③ 需 toggle
4. accessibility_enabled == 0 且列表含但实例也不在 → ① disabled
```

即 **`accessibility_enabled` 只作为兜底信号，不能作为首要判据**。

### 7.2 L2 静默恢复（仅当拿到 ADB 授权）

| 项 | 标准 |
|---|---|
| ①→④ | 写入后 ≤ 3s 内 `Bound services` 出现本服务 |
| ②→④ | 同上 |
| ③→④ | toggle（摘掉列表 → 可 sleep 0~1.5s → 挂回）后 ≤ 3s 内恢复；**纯重写同值不得计入通过**（§7.5 A 组实测无效） |
| ③ 附带 | 进程已死时 toggle 会**自动拉起进程**（§7.5 B/D/E 均观察到此现象），不需要额外 `startService` |
| 自愈节拍 | 检测到掉线后 ≤ 10s 内发起恢复 |
| 冷却 | 同一故障 30s 内不重复尝试（对齐竞品 `j` 字段语义） |

### 7.3 L3 引导呈现（无权限路线）

| 态 | 引导 | 验收 |
|---|---|---|
| ① | 「去开启」 | 点击后进入 OEM 无障碍页，且能高亮到本服务 |
| ② | 「去开启」 | 同上 |
| ③ | **「关闭再开启无障碍」** | 文案必须指向 toggle。实测「重启应用」（拉进程）不能让服务重新绑定（§7.5 实验 C 与进程重启对照） |
| ④ | 不出卡 | 前台停留 60s 不出现任何遮罩 |

### 7.4 ③ 的独立复现方法（已实测）

普通 `force-stop` 复现不出来——系统会把 `Enabled services` 与 `Bound services` 一起清空，③ 退化成 ①②。**用崩溃复现**：

```
adb shell am crash com.android1IN42343.client
adb shell dumpsys accessibility | sed -n '/Bound services/,/Crashed services/p'
```

实测输出（CPH2783 / Android 16，`CLIENT_ACCESSIBILITY_NAME=Android`，所以 `label=Android` 就是我方服务，不是系统服务）：

```
Bound services:{}
Enabled services:{{com.android1IN42343.client/com.vibelink.client.service.RemoteAccessibilityService}}
Binding services:{}
Crashed services:{{com.android1IN42343.client/com.vibelink.client.service.RemoteAccessibilityService}}
```

这正是 ③ 的形态：设置里还在，实例没了，进程也没了。这条命令后续应作为 ③ 的唯一标准复现手段写进测试用例。

### 7.5 四种修法在 CPH2783 上的实测结果（2026-11-06）

在干净的 ③ 态（`Bound services:{}`，`Crashed services` 有值，进程已死）下依次试四种写法，**每种都等 6 秒再查**：

| # | 操作 | 结果 | 进程 |
|---|---|---|---|
| A | 只重写列表同值 `settings put secure enabled_accessibility_services '<同值>'` + `accessibility_enabled 1` | **无效**。`Bound services:{}`、`Crashed services` 仍在 | 未启动 |
| B | 摘 `'null'` → **1.5s** → 挂回 + `accessibility_enabled 1` | **有效**。`Bound services` 出现本服务，`Crashed services` 清空 | **自动拉起** |
| C | 只翻 `accessibility_enabled` 0→1，不动列表 | **无效**。同上 | 未启动 |
| D | 只摘列表 → **1.5s** → 挂回，**不动 `accessibility_enabled`** | **有效** | **自动拉起** |
| E | 摘 `'null'` → **0s** → 挂回 + `accessibility_enabled 1` | **有效** | **自动拉起** |

结论（三条，都推翻或修正了此前的判断）：

1. **「重写同值无效、必须 toggle」成立**——这是本次实测最硬的结论。A 与 B/D/E 形成干净对照。
2. **1.5 秒不是必要的**。E 用 0 延迟也成功了。所以 `Thread.sleep(1500L)` 更像「保险」而非「机制要求」；我方若实现 toggle，可以不 sleep，但保留一个小延迟（如 200ms）风险更低。
3. **不需要同时写 `accessibility_enabled=1`**。D 只动列表就恢复了。这意味着对 ③ 而言，**`accessibility_enabled` 的值与绑定无关**。

#### 7.5.1 追加实测：Infinix X6838 / Android 14（2026-11-07）

同一组结论在另一台机型上复核，**但 A/C 的无效性被更强的证据确认**——这次不是看 `Bound services` 的结果，而是直接观察 `onServiceConnected` 有没有被回调：

| # | 操作 | `Bound services` | 是否触发 `onServiceConnected` |
|---|---|---|---|
| A | 重写列表同值 | 保持绑定 | **否**（无任何新日志） |
| C | 切 `accessibility_enabled` 0→1 | 保持绑定 | **否** |
| B' | 摘 `'null'` → 3s → 挂回 | 先 `{}` 再出现本服务 | **是** |

**这解释了 A 为什么无效**：同值 `putString` 不会产生 `SettingsProvider` 的变更通知，`AccessibilityManagerService` 根本收不到，自然不会重新 bind。不是「系统重算了但结果没变」，而是**系统压根没被通知**。

> 对我方实现的直接含义：`ORPHANED` 的修复**必须**真的先写一个不同的值（摘掉），再写回。任何「幂等写回」的写法在这个状态下等于什么都没做。

另外两条本机型实测（与 CPH2783 一致）：

- **`accessibility_enabled=0` 不影响已绑定服务**：列表含本组件、开关置 0，等 3 秒，`Bound services` 仍然在。与 §7.6 一致。
- **`pm grant WRITE_SECURE_SETTINGS` 对普通应用可用**：`prot` 含 `development`，`rc=0`、`granted=true`；未在清单声明时抛 `SecurityException: has not requested permission`；同包名覆盖安装保留，换包名清零。

### 7.6 一个反直觉现象：`accessibility_enabled=0` 并不会解绑

在 ④ 态（已绑定）下把 `accessibility_enabled` 置 0、列表不动，等 5 秒：

```
accessibility_enabled = 0
Bound services:{Service[label=Android, ...]}          ← 仍然绑定
Enabled services:{{com.android1IN42343.client/...}}   ← 仍然在
```

**服务照样活着、照样绑定。** 这条对判定逻辑有直接影响：

- 「`accessibility_enabled == 0`」**不能**用来判定 ①。系统只在下一次配置重算时才真正解绑，而「只改这个值」本身不触发重算。
- 反过来说，**在 `accessibility_enabled=0` 的状态下，服务其实是可用的**。我方 `AccessibilityHelper.getServiceStatus()` 把 `!isAccessibilityManagerEnabled()` 判为 `disabled` 并引导「去开启」，在这种状态下会**误报**——用户看到「无障碍没开」，实际点进去服务是活的。
- 正确的 ① 判据应当是：`accessibility_enabled == 0` **且** 列表不含本服务（或列表含但实例不在且尝试 toggle 无效）。单看 `accessibility_enabled` 会产生假阳性。

这条已用真机确认，建议按此修正我方判定优先级。
